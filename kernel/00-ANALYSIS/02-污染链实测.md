## 2. `state status` 的耗时与输出

| 测什么 | 怎么测 | 数字 |
|---|---|---|
| 单次耗时 | 计时器包住一次真实调用 | **3.9–8.3 秒**（见下方说明） |
| 输出体积 | 标准输出的字节数 | **12,067 B / 12,085 B**（两次实测，见 §12-2） |
| 输出行数 | 按行数 | **67 行**（两次一致） |
| 其中"历史缺口回灌" | 匹配 `缺少当前责任/文件的实际收据` 的行 | **7,181 B（59.5%）、25 行**（两次一致） |

> **关于耗时：这是区间，不是单值。**
> 第一次记录 **8,289 ms**；第二次复测 **3,896 ms**（纯 Python `subprocess`）与 **4,051 ms**（PowerShell 计时器）。

> 再逐行 `json.loads`）两次完全一样。
> **"慢"这个结论不变，只有倍数浮动。所以本文只给区间，不给单值。**

**复现命令（耗时）**

```powershell

$sw = [System.Diagnostics.Stopwatch]::StartNew()
$out = & python (Join-Path $root 'hub\tools\state.py') status --product $root 2>&1 | Out-String
$sw.Stop()

"output_bytes = $([System.Text.Encoding]::UTF8.GetByteCount($out))"

```

**复现命令（只测缺口那一块）**


**复现命令（纯 Python 读原始 stdout，最准）**

```powershell
python -c "import subprocess,time,sys; t=time.perf_counter(); p=subprocess.run([sys.executable,r'D:\临时项目\hub-dock\hub\tools\state.py','status','--product','.'],capture_output=True,cwd=r'D:\临时项目\hub-dock'); e=(time.perf_counter()-t)*1000; b=p.stdout; print('rc',p.returncode); print('elapsed_ms',round(e)); print('stdout_bytes',len(b)); print('stdout_lines',b.count(b'\n')); g=[l for l in b.split(b'\n') if '缺少当前责任/文件的实际收据'.encode() in l]; print('gap_lines',len(g)); print('gap_bytes',sum(len(l) for l in g))"
```

### 2.1 那 25 行长什么样

它们是这个意思（原文照抄）：

```
  - storage-recovery：storage_integrity:corrupt-mount-blocks-delete,… 缺少当前责任/文件的实际收据；缺少当前对象的独立评估来源；…
  - api-safety：local_api_safety:provider-no-redirect,… 缺少当前责任/文件的实际收据；…
  - load-fail-closed：startup_flow:load-fail-closed-before-write,http-load-forces-no-launch 缺少当前责任/文件的实际收据；…
```

**这是"历史上某次探针没留下收据"的记录，不是"现在卡住了"。**
但它每场开工都被读回来，占了输出的 **59.5%**。

## 3. 慢的根因：全量读 + 逐行解析

| 测什么 | 位置 | 数字 |
|---|---|---|
| 根因函数 | `hub/tools/hub_io.py:121` `def read_ledger(hub):` | — |
| 一次读全 | `hub/tools/hub_io.py:127` `text = f.read_text(encoding="utf-8-sig")` | 一次读 **26 MB** |
| 逐行解析 | `hub/tools/hub_io.py:130-140` `for i, line in enumerate(text.splitlines(), 1): … json.loads(line)` | 逐行 |
| 纯 PowerShell 复现同一件事 | 见下 | **3,672 ms** |

**复现命令（看代码）**

```powershell
$l = [System.IO.File]::ReadAllLines('D:\临时项目\hub-dock\hub\tools\hub_io.py')
121..140 | ForEach-Object { "{0}: {1}" -f $_, $l[$_-1] }
```

**复现命令（PowerShell 逐行复现 3,672 ms）**

```powershell
$sw = [System.Diagnostics.Stopwatch]::StartNew()
$n = 0
foreach ($line in [System.IO.File]::ReadAllLines('D:\临时项目\hub-dock\.hub\ledger.jsonl')) {
  if ($line.Trim()) { try { $null = $line | ConvertFrom-Json; $n++ } catch {} }
}
$sw.Stop()
"parsed = $n"
"elapsed_ms = $($sw.ElapsedMilliseconds)"
```

> **白话**：程序为了回答"现在做到哪了"，先把 26 MB 全部读进内存，再一行一行解析成对象。
> 慢不是因为账本难读，是因为**每次都从头读到尾，一个字节都不复用**。

## 4. 常驻注入的三个来源

| 测什么 | 位置 | 数字 | 复现 |
|---|---|---|---|
| 静态常驻文件只有 2 个 | `engine.py:1034` `for name in ("AGENTS.md", "FUSION.md")` | — | 见下 |
| `hub/AGENTS.md` 字节 | 磁盘 | **26,342 B** | `(Get-Item …).Length` |
| `hub/FUSION.md` 字节 | 磁盘 | **4,591 B** | 同上 |
| 静态盘合计 | 相加 | **30,933 B** | 同上 |
| **实际注入整块** | 宿主入口文件里 `# >>> hub-dock hub >>>` … `# <<< hub-dock hub <<<` 之间的实测字节 | **36,685 B** | 见下 |
| 其中运行时动态生成 | 36,685 − 30,933 | 约 **5,752 B** | — |
| 标记块写法 | `engine.py:1050-1051` `hub_marker()` 包 `# >>> hub-dock hub >>>` | — | 见下 |
| 运行时生成的技能名清单 | `engine.py:1002-1028`，8 大领域 `engine.py:1008-1015` | **92 个硬编技能名** | 见下 |
| 大路名生成 | `engine.py:955-979` | — | 见下 |

> **两个口径都要看**：
> **30,933 B** 是磁盘上那两个文件的和。
> **36,685 B** 是**模型每一场真正读到的整块**——多出来的 5,752 B 是 `engine.py` 运行时生成的技能名清单、
> 大路名、路径占位符替换后的结果。**这才是"每场固定开销"的诚实数字。**

> ### 📏 本文的一条硬规则：实测 > 估算
>
> **所有对外数字一律用实测值；估算值只能作为交叉印证的旁注，并且必须写明差异原因。**
>
> 这条规则是被一条错误估算逼出来的，记录在案：
>
> | 项 | 估算 | 实测 | 差 |
> |---|---|---|---|
> | 旧中枢每场注入量 | 26,342 + 4,591 + **估 3,750** = **34,683 B** | **36,685 B** | **+2,002 B** |
>
> 3,750 是**估的引擎生成技能名清单**；实测运行时生成部分是 `36,685 − 30,933 = 5,752`，比估的多 2,002 B。
> 两个数都不是猜的，但**只有实测那个能对外说**。
>
> **复现实测值**（量宿主入口里旧中枢整块）：
>
> ```powershell
> $h = "$env:USERPROFILE\.dsh\AGENTS.md"
> $t = [System.IO.File]::ReadAllText($h)
> $enc = [System.Text.Encoding]::UTF8
> $b = $t.IndexOf('# >>> hub-dock hub >>>')
> $e = $t.IndexOf('# <<< hub-dock hub <<<')
> $blk = $t.Substring($b, $e + 20 - $b)
> "旧中枢块 = $($enc.GetByteCount($blk)) B / $(([regex]::Matches($blk, "`n")).Count + 1) 行"
> "整个文件 = $($enc.GetByteCount($t)) B"
> ```
> → 实测：**36,685 B / 292 行**，整个文件 38,762 B。

**复现命令（静态常驻 2 文件 + 字节）**

第 3 个坑修好之后，**打包产物 `dist/hubcore/` 没有重打**，
于是**主人真正会跑的那条命令仍然是坏的**（§11 姿势 4 实测 exit 1）。

**三个修复只落地了 1/3**，`dist/` 是修复前的旧构建（产物 mtime 07:07:30 < 源码 07:15:23）。

**为什么测试没抓到**：测试跑的是**源码树**，不是**产物**。
**源码绿 ≠ 装出去的能用。**

### 13.2 一条可执行的规矩

> ## 📜 规矩：凡是写进提示词或文档的命令，必须至少有一条测试**真的执行它**。
>
> 三条细则：
>
> 1. **提示词里出现的每一条命令，都要有一条测试跑它，并且断言退出码。**
>    `CORE.md:24` 的 `python ctxiso/cli.py pack --product … --intent "…"` 就是例子——
>    它当时写在最显眼的位置，却从来没被执行过一次。
> 2. **断言"能跑"，不只断言"文件在"。** 文件存在 ≠ 命令能用。
>    本项目已经吃过两次这个亏（坑 1、坑 3）。
> 3. **测试必须跑"要发出去的那一份"，不是源码那份。**
>    对打包器来说，就是：`dist/hubcore/` 要么从源码重新生成后再测，
>    要么加一条**产物与源码同源**的检查（逐文件 sha 或 mtime 比对）。
>    **只测源码的测试，测不出"忘了重打包"这种故障。**
> 4. **（可执行）加一个"对产物跑一遍"的最小冒烟**，挂在"产物同源检查"变绿**之后**：
>    至少四种调用姿势 + `state.py --help`，全部对着 `dist/hubcore/` 跑，断言退出码。
>    **这条不加，"忘了重打包"还会再犯**——因为源码树的测试永远看不见它。
>    ⚠️ 见 §13.3：同源检查现在**会误报**，它变绿之前这条冒烟挂上去也是空的。
>
> **配套的验收口径**（建议进 `05-tests` 场景 1 的断言）：
> **断言 `pack` 的体积 ≤ 6,000 B，不要断言它等于某个具体字节数**——
> 包体积随意图长度、项目目标文本、长期资料条数浮动（实测 2,874 B / 3,060 B 都出现过），
> **只有 6,000 B 那个硬顶是规格，其余都是快照。**

### 13.3 ⚠️ 同源检查 `check_dist_sync.py` 现在**会永久误报**

统筹已落盘 `02-hubcore/check_dist_sync.py` 并接进心跳。本轮实跑：**checked 108 / same 56 / exit 3**。
**映射本身对，但它拿"变换前的源码"和"变换后的产物"比原始 sha，
而 `pack.py` 本来就要改写一批文件——所以重打之后它还是红的。**

**逐项核对了 5 个代表（全部是合法变换，不是产物旧）**：

| 文件 | 源 → 产物的差别 | 性质 |
|---|---|---|
| `templates/cli-tool.phases.json` | `.agents/skills/cli-tool/SKILL.md` → `workflows/cli-tool.md` | 路径改写 |
| `docs/methods/mobile-reverse.md` | `<hub>/tools.local.json` → `tools.local.json` | 路径改写 |
| `docs/methods/INVARIANTS.md` | `workflows/review/SKILL.md` → `docs/methods/review.md` | 路径改写 |
| `docs/RESPONSIBILITY-PROTOCOL.md` | `speech_land.py` → `tools/speech_land.py` | 路径改写 |
| `workflows/exe-rebuild.md` | `../INVARIANTS.md` → `docs/methods/INVARIANTS.md` | 路径改写 |
| `tools/state.py` | `hub-lean` → `hubcore`（2 行） | **旧项目名改写**（`pack.py:77` 注释明写"只在包副本上换掉"） |
| `tools/hub_io.py` | `hub-lean` → `hubcore`（1 行） | 同上 |
| `AGENTS.md` | **逐行完全相同**（差异行 0），但 sha 不同 | **行尾变换**（产物是 CRLF 243 处，源码是 LF） |

`missing_in_dist` 那 **19 个也是设计如此**，不是漏打：

| 文件 | 为什么不在包里 |
|---|---|
| `own_skill.py`、`skill_pull.py` | `pack.py:42` `SKILL_TOOLS`，只在 `--with-skill-tools` 时带（默认不带，因为带远端地址） |
| `test_*.py` 共 17 个 | `pack.py:43` `TEST_TOOLS`，测试不进包 |

**所以现在的判词"产物是旧的：33 个文件内容不同、19 个文件根本没进包。重跑 `pack.py` 之后再装。"
有两重错**：那 19 个永远补不上；那 33 个里大部分重打也不会变。

**危害不是"多报一次"，是"报错了还给出错误的修法"**——
而且它接进了心跳。**一个会喊狼来了的检查，最后一定被无视；
被无视之后，它本来能抓到的真故障也就一起丢了。**

**修法（按代价从小到大）**：

1. **立刻**：把 `SKILL_TOOLS` + `TEST_TOOLS` 从 `PAIRS` 里剔掉（`pack.py:42-43` 已有现成常量），
   并在算 sha 前**归一化行尾**（`\r\n` → `\n`）。这两步消掉约 20 个假阳性。
2. **正确做法**：**别拿变换前的源码去比变换后的产物**——
   让 `pack.py` 在打包时把**每个产物文件的 sha256** 写进 `bundle-meta.json`，
   `check_dist_sync.py` 改成**拿产物和"自己该是什么样"比**。
   唯一能保证真绿的办法，是**重跑一次变换拿期望值**（可以把 `pack.py` 的 `build()` 输出到临时目录再比，不碰 `dist/`）。
3. **顺带**：`missing_in_dist` 要区分"故意不打包"和"漏打包"——前 19 个是前者。

### 13.4 坑 4：BOM 被静默丢弃——**卸完之后主人的文件已经不是那个文件**

打包器在验收时自己发现的（`03-bundle/_scratch*.py` 是当时的复现脚本）。

| 测什么 | 数字 |
|---|---|
| 症状 | 装 → 卸往返后，入口文件**正文一模一样**，但**字节不同** |
| 原因 | 解码时把 BOM 当正文剥掉，写回时没补回去 |
| 后果 | SPEC §4 的验收是「卸载后宿主 `AGENTS.md` 与装之前**逐字节相同**」。BOM 掉了 = **这条验收不成立**，而且**主人在界面上一个字都看不出来** |
| 触发条件 | **只在主人用带 BOM 的编辑器写入口文件时发作**（记事本、部分国产编辑器）。平时测不出来 |

**修法**（现在已落盘）：

| 位置 | 做法 |
|---|---|
| `_bundle_lib.py:116-132` | `BOM = b"\xef\xbb\xbf"`；`decode()` 先剥、`encode(text, bom)` 再补，**成对使用** |
| `install.py:279-282` | 注释明写：直接 `original.decode()` 会把 BOM 变成正文里的 U+FEFF，写回时又补 BOM 字节 → **双 BOM，卸完差 3 字节** |
| `uninstall.py:112-117` | `bom = original.startswith(BOM)`；`stripped_bytes = (BOM if bom else b"") + stripped.encode("utf-8")` |

> **教训**：**"正文一样"不等于"文件一样"。**
> 这一类和 §13.1 那个"收据在撒谎"是同一族——
> **凡是验收标准写的是"逐字节相同"，就必须真的按字节比，不能比文本。**

### 13.5 坑 5：`pack.py` 的适配锚点与素材脱节 → 重新构建失败

**本轮实测复现**（`check_dist_sync.py` → exit 3）：

```json
{ "ok": false, "why": "重新构建失败，产物新鲜度无从判断", "rc": 1,
  "tail": "ctxiso 适配锚点没命中，素材可能已改版。\n  文件：__init__.py\n
           找不到：'3. 本包所有状态写在 work/context-isolation/state/ 下，不写进 .hub/。'" }
```

**根因**：`pack.py:139` 拿这一行当**锚点**，把它改写成产品味的说法（`:140`）：

```python
"3. 本包所有状态写在 work/context-isolation/state/ 下，不写进 .hub/。",   # ← 锚点
"3. 本包所有状态写在本包的 .state/ 下，不写进 .hub/，也不写宿主家目录根。"),  # ← 改写结果
```

**而源码 `ctxiso/__init__.py:8` 已经被手工改成了第三种说法**：

```
3. 本包所有状态写在包内 `state/` 下，不写进 `.hub/`，不写进产品目录。
```

**锚点对不上 → `pack.py` 拒绝构建 → `check_dist_sync.py` 退出 3 → 场景 9.5j 红。**

> **这和前三个坑是同一个病**：改了源头，**配套的那一半没跟上**。
> 坑 1/2/3 是"调用方和定义方没对齐"，坑 5 是"打包器和素材没对齐"。
> **同一个病第四次复发，而且复发在最不该复发的地方——那个专门用来抓"产物过期"的检查。**
>
> **更狠的一层**：这个检查一旦坏了，它报的是"重新构建失败"，
> **主人会以为产物过期去重打 `dist/`，而真因是锚点过期。** 又是**报错了还给出错误的修法**。
>
> **修法**：`pack.py` 的锚点不该写死一整句话。
> 该按**稳定的语义片段**匹配（如 `本包所有状态写在` + 随后的目录名），
> 或者**匹配不上就明确报"锚点过期，请更新 pack.py"**，而不是笼统的"素材可能已改版"。

### 13.6 四个坑的同一个根子

| 坑 | 谁和谁没对齐 | 什么时候才发现 |
|---|---|---|
| 1 · `status` 从没工作过 | `archive.read_history` 签名 ↔ `cli.py` 调用方 | T4 的测试 |
| 2 · `read --intent` 每次成功都崩 | 写了 `hashlib.sha8` ↔ 标准库没有这个 | T4 的测试 |
| 3 · 提示词里最常调的命令是坏的 | 写进 `CORE.md` 的命令 ↔ 没跑过 | 装到产物上才炸 |
| 4 · BOM 被静默丢弃 | 装卸的字节标准 ↔ 解码/写回的实现 | 打包器验收 |
| 5 · `pack.py` 锚点过期 | 打包器 ↔ `ctxiso/__init__.py` | 跑 `check_dist_sync.py` |

**一句话**：**这五个坑全部是"我以为它对上了"。**
没有一次是"程序算错了"——**全都是"没真的跑一遍"**。
