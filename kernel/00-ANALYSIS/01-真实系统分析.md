# 01 · 真实系统分析

> 这份文档回答一个问题：**旧中枢（`hub-dock`）到底是怎么把东西"记下来"又"读回去"的。**
> 全部结论都有 `文件:行号` 或实测数字撑着。数字一个都没改。
> 面向没有编程基础的读者。第一次出现的术语后面都跟一句白话解释。

---

## 0. 一句话结论

旧中枢把每一次干活都**自动记在磁盘上**，然后又用**常驻提示词里的文字规定**，让每一场新对话**必须把这份磁盘记忆读回来**。
磁盘上那份 26 MB 的账本，加工速度慢、单条膨胀到 23 KB；读回来的长文里 **59.5% 是历史缺口**。
**这套系统里没有任何一个模块负责"上下文压缩"**——压缩完全交给宿主智能体自己总结，于是"当时上下文里的一切"（包括插头、包括那段缺口长文）被二次固化，再灌回下一场。

**保存与读取的耦合点，就在常驻提示词的那几句话里，不在代码里。**

---

## 1. 几个白话词

| 术语 | 白话解释 |
|---|---|
| **常驻提示词** | 每次开新对话，智能体必读的那一大段规则文字。相当于"上班第一天贴在墙上的制度"。 |
| **上下文** | 智能体这一次能"看见"的全部内容：制度 + 你说的话 + 工具返回的结果。窗口就那么大，塞不下太多。 |
| **token** | 模型的计量单位。中文大约 1 个字 ≈ 1~2 个 token。上下文满了就要"压缩"。 |
| **账本（ledger）** | 一个只追加、不改写的流水文件，一行一条记录，记"谁在什么时候做了什么、结果如何"。 |
| **回读** | 记下来的东西被重新读进上下文。 |
| **污染** | 跟"这一轮要干什么"无关的旧内容混进上下文，让模型把过去的任务当成现在的任务。 |
| **物理门 / 探针** | 机器真的跑一次真实产物（比如真的启动程序、真的点一次按钮），留下"收据"。收据才算证据。 |
| **死链** | 文档里写了一个路径，但那个文件其实不存在。 |

## 2. 真实结构：一条线走完

### 2.1 入口在哪

智能体（Codex / Claude / Cursor / dsh …）启动时，先读它自己家目录里的规则文件。
旧中枢不改这份文件整份，**只在最前面插一个带标记的块**（标记写法见 `work/v0.1.0/hubdock/engine.py:1050-1051`）：

```python
def hub_marker(...):
    return "\n# >>> hub-dock hub >>>\n" + hub_plug_body(...) + "\n# <<< hub-dock hub <<<\n"
```

装的时候是控制台（`engine.py`）生成这块文字，追加到宿主入口文件。宿主原文一个字不动。

### 2.2 上下文是怎么"产生"的

一次注入，智能体看到的东西分两块：

**A. 静态盘（每次都一样）**

| 块 | 字节 | 证据 |
|---|---|---|
| `hub/AGENTS.md` | 26,342 B | 磁盘实测 |
| `hub/FUSION.md` | 4,591 B | 磁盘实测 |
| 合计常驻（磁盘静态盘） | **30,933 B** | 两文件相加 |
| **实际注入整块**（模型每场真正读到的） | **36,685 B** | 宿主入口文件里 `# >>> hub-dock hub >>>`…`# <<< hub-dock hub <<<` 之间实测 |

生成代码在 `work/v0.1.0/hubdock/engine.py:1033-1043`：

```python
books = []
for name in ("AGENTS.md", "FUSION.md"):
    text = (HUB_DIR / name).read_text(encoding="utf-8")
    books.append(bind_hub_text(text.replace("\r\n", "\n").strip()))
body = "\n".join(lines)
if books:
    return body + "\n\n" + "\n\n".join(books)
```

**注意：只有这 2 个文件是常驻的**。别的地方（技能书、席位稿）都不是常驻。

**B. 动态块（每次装机现场生成，量比静态盘还大）**

`engine.py:1002-1028` 会在运行时扫宿主技能夹，**硬编出 8 个领域、共 92 个技能名**（4+14+10+10+8+15+13+**18**）的清单塞进注入里。原文：

```python
f"全域专业技能库已全量部署至本智能体 skills 夹（共 {len(present)} 本），按技术领域分类索引。……"
categories = [ ("逆向与攻防总控", [...4 本...]), ("原生二进制逆向", [...14 本...]), ... ]
```

这就是任务书里说的"约 100 个技能名"。**精确数是 92 个硬编名**（`engine.py:1008-1015`），实际渲染多少取决于那台机器的技能夹里装了哪些——`engine.py:1019` 会按本机存在的技能过滤。**"硬编 92 个"是稳定口径，"渲染出几个"逐台机器不同。**
另有 `engine.py:955-979` 生成"本场挂着底模 X + 技能包 Y"的大路名。

> 一句话：**旧中枢每场对话的固定开销 = 30,933 B 静态盘 + 约 5,752 B 运行时生成（其中一份 92 项技能名清单）= 实际注入 36,685 B。**

### 2.3 上下文是怎么"写入"的（往磁盘写）

分两条完全不同的路：

**路 1 · 机器账本（自动、只追加）**

`hub/tools/state.py` 把每一次操作写成一行 JSON，追加进产品根的 `.hub/ledger.jsonl`。

实测这个文件：

| 指标 | 实测值 |
|---|---|
| 体积 | **26,029,540 B** |
| 行数（= 事件数） | **1,118** |
| 平均每条 | 约 23 KB |

事件类型分布（全部 12 种，合计 1,118）：

| 事件类型 | 条数 |
|---|---|
| `physical_probe` | 518 |
| `work_attest` | 269 |
| `candidate` | 212 |
| `work_define` | 42 |
| `owner_seen_observation` | 23 |
| `work_retire` | 18 |
| `work_enter` | 10 |
| `work_leave` | 10 |
| `confirm` | 7 |
| `reopen` | 5 |
| `plan` | 2 |
| `rebind` | 2 |

**为什么单条能到 23 KB？** 因为一条探针事件里内嵌了这些东西：

- `observed.json`：一整份快照，**30+ 个键，其中大量是 `null`**
- `assertions` 数组：这一次每个断言过没过
- `candidate_paths`：**30 条**候选路径
- `work_bindings`：**逐文件 sha**（每个文件一个哈希字符串）

`hub/AGENTS.md` 自己也写了这句：「不能只靠报告说完成，要机器收据」——收据就是这么收的。**代价是体积。**

**路 2 · 人写的长期资料（自动追加、只增不减）**

| 文件 | 实测字节 | 谁写 |
|---|---|---|
| `OWNER-SPEECH.md` | 73,441 B | `hub/tools/speech_land.py`（从对话里抽主人原话） |
| `CHANGES.md` | 151,135 B | `hub/tools/hub_cmds.py` |
| `.hub/requirements.jsonl` | 72,475 B | `state.py require --append` |
| `PROJECT-MEMORY.jsonl` | 28,758 B | `feature_set.py --apply` |
| `WORK-HANDOFF.md` | 16,999 B | 人写的交接纸 |

产品根 `.hub/` 里还有：`contract.json` 6,190 B、`manifest.json` 74,541 B、`physical-gates.json` 30,190 B、`shift-ticket.json` 1,971 B。

**这些全部是"只写不读"的池子。** 写进去很勤快，读回来是另一回事。

### 2.4 状态 / 进度 / 交接分别存在哪

| 想知道什么 | 去哪看 | 权威性 |
|---|---|---|
| 当前产品是谁、mission、候选、停点 | `.hub/contract.json` + `.hub/ledger.jsonl` → `state status` | **唯一权威** |
| 做过什么、每次结果如何 | `.hub/ledger.jsonl` | 唯一流水 |
| 主人说过什么原话 | `OWNER-SPEECH.md` + `.hub/requirements.jsonl` | 不可覆盖 |
| 改了什么 | `CHANGES.md` | 改动图 |
| 上一班干到哪 | `WORK-HANDOFF.md` + `SHIFT.md` + `.hub/shift-ticket.json` | 交接纸 |
| 哪些阶段必须过哪些机器检查 | `.hub/physical-gates.json` | 硬门 |

**一句话：旧中枢没有"进度条"这个文件，进度就是账本的投影**——跑一次 `state status` 现算出来给你看。

### 2.5 怎么被"回读"

**这是整份文档最关键的一节。**

回读不是代码强制，是**常驻提示词用文字规定**的。旧 `hub/AGENTS.md` 的 §4「换班续上」逐条规定：

```
hub/AGENTS.md:97  上班必须接班。新智能体打开项目夹，读完这份主插件后第一件事：
                  python <hub>/tools/shift.py take --product <项目夹>
                  再读 WORK-HANDOFF.md
                  再 git status --short / git branch --show-current / git log -1 --oneline / git diff --stat
                  有账本再 state status --product <项目夹>
                  有地图再 map_show
                  禁止凭聊天记忆重列门禁、地图、打包清单。
```

`hub/AGENTS.md:96` 规定留班那一半（`shift.py leave` + 更新 `WORK-HANDOFF.md`）。
`hub/AGENTS.md:158` 又规定："开工读图：先跑 `map_show.py`，**禁止整仓重读**。"

> **把"写"和"读"缝在一起的就是这几行字。**
> 智能体是照着这几行字去跑的，代码里没有任何一行说"新对话必须读账本"。
> 所以：**删掉这几行字，这条污染链就断了。** 这是后面新系统的抓手。

### 2.6 压缩在哪

**结论：不存在。**

```
work/v0.1.0/hubdock/  递归搜索 summar / compact / trim / distill / forget
→ 0 命中（Python 源码 0 命中，def 形式 0 命中）
```

也就是说：**没有任何程序负责"把这一场的上下文压短"。**
压缩交给宿主智能体自己总结。而宿主的总结对象是"当时上下文里的一切"——**包括那 36,685 B 插头、包括那 12,067 B 缺口长文**。

于是：历史缺口被写成"总结"→ 总结又变成下一场的背景 → 下一场再读一次账本 → 再总结一次。
**这不是压缩，这是历史的二次固化。**

## 3. 真实污染链

下面是一条链。**每一步都标了文件与行号**，从"写"到"再写"闭环。

```
[主人开会/干活]
   │
   │  ① 机器把每一步追加进账本
   ▼
.hub/ledger.jsonl   ← hub/tools/state.py
   │  实测 26,029,540 B / 1,118 条，平均约 23 KB/条
   │  膨胀源：observed.json（30+ 个 null 键）、assertions 数组、
   │         candidate_paths（30 条）、work_bindings（逐文件 sha）
   │
   │  ② 新对话开始。常驻提示词用【文字】要求回读：
   │     hub/AGENTS.md:97 「上班必须接班 … 有账本再 state status --product <项目夹>」
   │     hub/AGENTS.md:158 「开工读图 … 禁止整仓重读」
   ▼
python hub/tools/state.py status --product .
   │
   │  ③ 慢的根因在这里：
   │     hub/tools/hub_io.py:121  def read_ledger(hub):
   │     hub/tools/hub_io.py:127      text = f.read_text(...)      ← 一次读全 26 MB
   │     hub/tools/hub_io.py:130-140  for line in text.splitlines(): json.loads(line)  ← 逐行解析
   ▼
   │  实测：单次 3.9–8.3 秒（随磁盘缓存与负载浮动；根因不变）
   │
   │  ④ 输出回灌：12,067–12,085 B / 67 行（该数字随工作区状态漂移）
   │     其中 7,181 B（59.5%）、25 行是
   │     「…缺少当前责任/文件的实际收据」 ← 历史探针缺口，不是当前阻塞
   ▼
[智能体上下文]
   │  ⑤ 这 12 KB 长文原样进上下文
   │
   │  ⑥ 窗口满了 → 宿主智能体自己"总结"
   │     hubdock 全库无 summar*/compact*/trim* → 没有任何程序管这件事
   │     宿主总结的是"当时上下文里的一切"
   ▼
[压缩后的上下文]  ← 插头 + 缺口长文被二次固化
   │
   │  ⑦ 下一场再读同一份常驻提示词，再被文字要求再跑一次 status
   ▼
回到 ② ── 循环
```

### 3.1 链上每一环的实测数字

| 环 | 环节 | 数字 | 复现 |
|---|---|---|---|
| ① | 账本体积 / 条数 | 26,029,540 B / 1,118 条 | 见 `02-污染链实测.md` §1 |
| ① | 单条探针 | 约 23 KB | 同上 |
| ② | 回读触发点 | `hub/AGENTS.md:97` | 直接看文件 |
| ③ | 慢的根因 | `hub/tools/hub_io.py:121`（`f.read_text()` 在 `:127`，`json.loads` 在 `:135`） | 直接看文件 |
| ③ | 单次耗时 | **3.9–8.3 秒**（区间；第一次记录 8,289 ms，复测 3,896 / 4,051 ms） | 同上 |
| ④ | 输出体积 | **12,067–12,085 B** / 67 行（随工作区状态漂移） | 同上 |
| ④ | 历史缺口占比 | 7,181 B（59.5%）/ 25 行 | 同上 |
| ⑥ | 压缩实现 | **0 个** | 同上 |

### 3.2 链旁边的第二条污染：常驻注入本身

污染不只从账本来，**常驻那一块也在变胖**：

| 项 | 数字 | 位置 |
|---|---|---|
| 静态常驻 2 文件 | 30,933 B | `engine.py:1034-1042` |
| **实际注入整块** | **36,685 B**（多出的 5,752 B 是运行时生成） | 宿主入口实测 |
| 运行时生成的技能名清单 | **92 个**硬编技能名，分 8 个领域 | `engine.py:1008-1015` |
| 同稿供 8 个宿主的席位稿 | `packs/hanshuang-codex-filecopy/original/寒霜v1.2.md` = **130,161 B**（约 59k token） | 经 `packs/*/meta.json` 的 `seats.*.prompt` 接线 |

**9 份席位稿**通过 `packs/*/meta.json` 接线写进宿主，其中 `寒霜v1.2.md` 一份供给 8 个宿主（claude / codex / cursor / dsh / gemini / grok / opencode / zcode）。
这一条链是"同一份 130 KB 文字，被 8 家智能体各自整份塞进上下文"。

### 3.3 链上还有一段"写了等于没写"

旧 `hub/AGENTS.md` 有 **6 处**句子在讲"完善中枢 / 优化中枢"：L12、L46、L167、L197、L210（整节标题）、L212。
而 `work/v0.1.0/hubdock/engine.py:802-813` 的 `_void_stale_source_identity()` **在注入前会用正则把它们作废**：

```python
def _void_stale_source_identity(text: str) -> str:
    """旧安装副本自称源仓、要走完善中枢的句子作废。"""
    out = _PERFECT_HUB_SHORT.sub("这场不要在这家智能体走完善中枢", text)
    out = _PERFECT_HUB_LONG.sub("这场不要在这家智能体走完善中枢。旧安装根不是源仓。", out)
    ...
```

**这 6 处在磁盘上占 token，注入时又被系统自己声明作废。** 典型的"写了等于没写还占地方"。

## 4. 哪些信息自动进上下文 / 哪些只落盘

| 信息 | 落在哪 | 会不会自动回上下文 | 凭什么 |
|---|---|---|---|
| 中枢掌舵书 | `hub/AGENTS.md` 26,342 B | **每场必进** | `engine.py:1034` 硬读 |
| 副插件分工 | `hub/FUSION.md` 4,591 B | **每场必进** | 同上 |
| 技能名清单（93 个） | 无文件，运行时生成 | **每场必进** | `engine.py:1002-1028` |
| 底模 / 副插件席位稿 | `packs/*/…`、`data/prompts/` | 挂了就**整份进** | `meta.json` 的 `seats.*.prompt` |
| 账本全量 | `.hub/ledger.jsonl` 26,029,540 B | **不直接进** | 程序从不注入它 |
| `state status` 的输出 | 运行时打印 | **会被倒进** | `hub/AGENTS.md:97` 文字要求 + 智能体照做 |
| `WORK-HANDOFF.md` | 产品根 | **会被读** | `hub/AGENTS.md:97` 文字要求 |
| 主人原话 | `OWNER-SPEECH.md` / `.hub/requirements.jsonl` | 不自动读，但要写 | 「一句一收」是硬规则 |
| 改动图 | `CHANGES.md` | 不自动读 | — |
| 项目地图 | `MAP.md` / `FEATURES.md` | `map_show` 才读 | `hub/AGENTS.md:158` |
| 技能书正文 | `hub/.agents/skills/*/SKILL.md` | 智能体自己点名才读 | 没有程序路由 |

**关键区分**：账本正文**从不自动进上下文**。真正污染的是 **`state status` 的输出**——它是"账本的一段投影"，被文字规定每场开工都要跑一次，于是 26 MB 的账本以 12,067 B 的形式每场回来一次。

## 5. 哪些机制该保留、哪些该隔离、哪些需要新增控制

### 5.1 该保留（这些是这套系统的真本事，砍了就是砍产品）

| 机制 | 为什么必须留 |
|---|---|
| 机器账本 `.hub/ledger.jsonl` | 唯一流水，删了就没法证明做没做。**问题不在存，在读。** |
| 物理门 + 探针收据 | 唯一能证明"东西真的能用"的东西。 |
| 停点与 `confirm` 需主人当面点头 | 防止工程方自己给自己批。 |
| 换班接班（`shift.py` + `WORK-HANDOFF.md`） | 保证"人换了活还是这一摊"。 |
| 主人原话只追加 | 需求不丢。 |
| `ctxiso` 侧车（新建） | 索引 334 ms、任务包有预算、按需读要意图。**它就是本节要的东西。** |

### 5.2 该隔离（内容留在盘上，但不许自己回来）

| 对象 | 现状 | 要改成 |
|---|---|---|
| 26 MB 账本 | 每次 `status` 全量 `read_text()` | 增量索引；查历史走索引，不碰大文件 |
| `state status` 的 25 行历史缺口 | 每场回灌 7,181 B | **当前阻塞**才进包；**历史缺口**只留一个计数指针 |
| `OWNER-SPEECH.md` / `CHANGES.md` | 写得很勤，读回来无差别 | 只出"索引行"（路径/大小/行数/一行用途），正文要带意图 |
| 压缩 | 完全交给宿主，宿主总结一切 | 压缩前先签"存活集"，压缩后只认存活集 |
| 席位稿 130,161 B | 同稿供 8 个宿主整份进 | 挂载时按宿主裁剪，或改成指针 |

### 5.3 需要新增的控制（旧系统完全没有的）

1. **意图门**：读任何长期资料正文之前必须声明"为什么现在需要它"，没声明就只给位置不给正文。`ctxiso` 侧车已经实现（`archive.py:74-120` 抛 `IntentRequired`）。
2. **预算**：任务包有硬顶（`config.json` 的 `pack_budget_bytes` = 6000 B），超了截断并写明截了什么。
3. **压缩存活集**：`compact.py` 规定压缩后只保留 7 个字段（intent / stage / goal / next / blockers / confirmed_decisions / constraints），掉出去的东西写进 `dropped.json` **按指针取回，不重新总结**。
4. **改前不动**：`guard.py` 给 34 个中枢受控文件取 sha 基线，随时能回答"旧系统还是原来那份吗"。
5. **只增不减**：`observe.py` 证明这次重构没让中枢少记东西（只查变小和消失，不查变大）。
6. **自包含**：装完把源仓整个搬走，系统仍能工作。

## 6. 明确回答：「当前是否存在『自动写入后又自动读取』」

### 答：**有。耦合点在常驻提示词的文字规定里，不在代码里。**

拆开说：

| 环节 | 是自动的吗 | 靠什么 |
|---|---|---|
| 写 | **是**，全自动 | `state.py` / `speech_land.py` / `hub_cmds.py` 每次干活顺手追加 |
| 读 | **半自动**——智能体确实每次都读，但**没有任何一行代码命令它读** | 纯靠 `hub/AGENTS.md:97` 那段「上班必须接班」的文字 |
| 两者之间 | **没有任何代码连接** | 无钩子、无拦截、无白名单 |

**所以：**

- 说"有自动耦合"是**不对的**——代码里查不到。
- 说"没有耦合"是**更不对的**——实际上每场都在发生。
- 准确的说法是：**耦合是"约定式"的，靠提示词施压，代码不设防。**

这一点对新系统是**好消息**：
不需要去改旧代码（规格书第 0 条硬约束"不改旧系统"），只要新系统**不写那几句话**，污染链就断了。
反过来，如果新系统原样抄了 `hub/AGENTS.md:97` 的换班条文，这 26 MB 账本还会每场回来一次。

**新系统的 `02-hubcore/AGENTS.md` §9 就是这个断点**：
「开工先取任务包，不跑全量账本」+「判断停点要权威全貌时才跑 `state status`，且只跑一次」+「知道文件存在 ≠ 读正文」。
§9.3 把原因写死成一句可执行的话：

> 问题从来不在"存不存"，在**记下来的东西什么时候又被读回去**。
