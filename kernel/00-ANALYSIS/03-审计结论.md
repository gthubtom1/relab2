## 1. 审计 A：提示词全量清单

**白话**：提示词 = 塞给智能体的说明文字。Tier = 分层。Tier1 是中枢自己的，Tier2 是副插件席位稿，Tier3 是没人接线的原稿。

### 1.1 Tier1 · 中枢本体（10 份）

| 分类 | 份数 | 清单 | 字节 |
|---|---|---|---|
| **ALWAYS**（每场必进） | **2** | `hub/AGENTS.md` / `hub/FUSION.md` | 26,342 + 4,591 = **30,933 B** |
| **按需**（要才读） | **5** | `work/v0.1.0/prompts/adapt-system.md`（7,361 B）<br>`work/v0.1.0/prompts/adapter-flow.md`（3,205 B）<br>`work/v0.1.0/prompts/derive-system.md`（4,899 B）<br>`data/prompts/adapt-system.md`（6,477 B）<br>`data/prompts/adapter-flow.md`（2,852 B） | — |
| **DEAD**（死的） | **3** | `work/v0.1.0/prompts/cartridge-contract.md`（1,508 B）<br>`work/v0.1.0/prompts/adapt-system.md` seed（7,361 B）<br>`work/v0.1.0/prompts/adapter-flow.md` seed（3,205 B） | 死重 **12,074 B** |

**ALWAYS 为什么只有 2 份？** 证据在 `work/v0.1.0/hubdock/engine.py:1034-1042`：

```python
for name in ("AGENTS.md", "FUSION.md"):
    text = (HUB_DIR / name).read_text(encoding="utf-8")
    books.append(bind_hub_text(text.replace("\r\n", "\n").strip()))
...
return body + "\n\n" + "\n\n".join(books)
```

**除这 2 个文件，其余中枢文档（`hub/docs/` 下 19 份、`hub/` 根级 8 份）都不进常驻。**

**「按需 5 份」里的重复要说明白**：磁盘上按需提示词一共 5 份文件，但它们**不是 5 份不同的内容**——
`adapt-system` 和 `adapter-flow` 各有**两份**（一份是出厂 seed，一份是主人/用户改过的稿）。
运行时按 `work/v0.1.0/hubdock/prompts.py:28-33` **用户优先**：

```python
user = user_prompt_path(name, root)
if user.is_file():
    return user.read_text(encoding="utf-8")   # 用户稿先
seed = ALLOWED[name]
if seed.is_file():
    return seed.read_text(encoding="utf-8")
```

所以**实际生效的只有 3 份**（`data/prompts/adapt-system.md`、`data/prompts/adapter-flow.md`、`work/v0.1.0/prompts/derive-system.md`）。

**DEAD 3 份的死法各不相同**：

| 死稿 | 怎么死的 | 后果 |
|---|---|---|
| `cartridge-contract.md` | **全仓 0 引用**（`.py` / `.md` / `.json` 全搜过） | 纯废纸，1,508 B 零收益 |
| `adapt-system.md` seed | 被 `data/prompts/adapt-system.md` 遮蔽 | **改 seed 对运行时无效** |
| `adapter-flow.md` seed | 被 `data/prompts/adapter-flow.md` 遮蔽 | 同上 |

**而且遮蔽稿比 seed 旧一版**（小 884 B / 353 B）。
**这是一个维护陷阱**：有人改 seed、以为生效了，其实运行时读的是那份旧的。

## 4. 合并结论：删技能库不会崩程序，坏的是文字指向

**这是三份审计加起来最值钱的一句。**

### 4.1 为什么能下这个结论

| # | 证据 | 说明 |
|---|---|---|
| 1 | `hub/tools/hub_io.py:43` 硬编 6 条 `PRODUCT_TYPES` | 产品线是写死的常量，**不是从技能库读出来的** |
| 2 | 48 个阶段槽位（去重 30 个不同 id）、56 处检查引用（22 个不同 id） | **与技能库零交集**：没有一条阶段靠技能名分派 |
| 3 | `hub/.agents/skills/README.md:45` 原文：「…这就是"你不断加 skill，AI 都能在对的流程点用上"，**全靠约定，没有 py 路由表**」 | **技能夹自己承认**没有程序路由 |
| 4 | 六线正文 0 次点名 `user-skills` / `packs` | 依赖全在中枢顶层三个文件，不在线里 |

### 4.2 所以真相比"崩不崩"更难受

**把 `hub/.agents/skills/` 整个删掉：**

- ✅ 程序**不会崩**。没有一条分支按技能名走。
- ❌ **但 `hub/AGENTS.md:109,113,114,118`、`hub/FUSION.md` 里那些"读配套中枢技能夹""用 `own_skill.py` 写技能"的句子会全部指向空气。**
- ❌ 六线的 `SKILL.md` 正文里那些 `../README.md`、`` `github` `` 会变成**死链**。
- ❌ 智能体照着文字去找，找不到，**要么卡住，要么自己编一个**。**这是最坏的一种失败：程序不报错，人也看不出来，智能体拿着幻觉继续干。**

> **一句话：坏的不是程序，是文字指向。**
> 所以新系统的做法不是"删技能"，而是**先把文字改成指针，再让不读指针也丢不掉底线**。

### 4.3 新系统已经做的三件事

| 做法 | 落在哪 | 效果 |
|---|---|---|
| 文字改成指针 | `build_hubcore.py` 的 `SUB_RULES`：`<hub>/.agents/skills/X/SKILL.md` → `workflows/X.md` | 指向变成本系统内真实存在的路径 |
| 死链直接删 | `LINE_RULES` 里 `vendor/reverse-skill` / `深度按 ../README.md` 整行删 | 2 条死链不再出现 |
| 移出的技能不许以书名残留 | `build_hubcore.py:290-297` 的 `parked_leak` 校验 | `github` / `own-skill` 的名字不许再以 `` `名字` `` 形式出现在交付件里 |

`--check` 三项全绿就是这三件事的验收。
