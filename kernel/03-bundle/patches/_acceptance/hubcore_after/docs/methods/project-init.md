# 项目初始化方法

对主人先白话：做到什么、还缺什么、下一步看哪。一次只说一扇窗、一个键。机械项自己跑；主功能给人话清单等人测；做不到当场说。两句不能互相吞掉。

本 skill **不是**从零做产品的主流程，也**不能**在「方案谈完了，开工搭项目」时当主书。主书仍是 `desktop-product` / `web-service` / `cli-tool`。不要把中枢源仓根或它里面的子夹当成产品夹。接手不要加载本本从零搭骨架。本本只嵌在桌面/网站/命令行阶段 1（架构与地基）：搭完脚手架立刻回到那本产品线，继续地基，不要在这里问接不接、不要在这里打包。用户只说了一句简单需求：去产品线先讨论补方案。方案没补到能推进之前，不要在这里搭骨架、不要先画窗口、不要先写页面。

## 起步就做对

- 建 git 基线（第一个 commit = 干净骨架）；装 pre-commit 密钥扫描。
- **先定文件夹再堆文件：** 要留下的（源码、当前工作拷贝、用户数据、秘密、安装包）写进 README；可整夹删除的只进产品根 `TEMP/`，产品 `.gitignore` 忽略 `TEMP/`。根目录一锅炖、到处临时文件 = 没开工。各版源码靠 git 定档回退，不要把版本堆进 `TEMP/`。
- 目录 / 命名 / 依赖清单（带版本）；README 写清"怎么跑起来"。
- 定数据存哪、配置存哪、秘密怎么放（不进 Git）。

## 别一上来堆

- 先能跑起来一个最小骨架，再按需求加，不预造一堆抽象。

## 和 state 配合

- 不要在这里当主书跑 `state init`。合同由产品线那本去建。架构决定 `record --kind arch`、模块 `record --kind module`。

## 别假装

- 脚手架生成 ≠ 能跑：起步就先让最小骨架跑通该产品线的一条可观察主动作（窗口出现 / `--help` / 退出码 0 不算）。
