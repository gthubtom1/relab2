# 规划方法（轻，别变成仪式）

对主人先白话：做到什么、还缺什么、下一步看哪。一次只说一扇窗、一个键。机械项自己跑；主功能给人话清单等人测；做不到当场说。两句不能互相吞掉。

本 skill **不是**从零做产品的主书，也**不能**顶替 `desktop-product` / `web-service` / `cli-tool` / `source-takeover` / `exe-rebuild`。用户只说了一句需求：去对应产品线先讨论。本本只嵌在已经选定的那条线里拆步；想清立刻回到那本产品线，不要在这里 `init`、不要在这里打包、不要在这里发 Release。

## 先抓主线

- 先说清"这次真正要的可观察结果是什么"，再排到那儿的最短可验证路线。
- 一次只走一条主线；旁支只有挡住主线时才升级。
- **一句简单需求禁止立刻写代码。** 先用人话把方案补全：要哪些功能、什么组件、怎么衔接、失败怎么办、数据放哪、缺什么、以后怎么卖（有源码：改界面或命令体验、问授权、打包；二开：改界面、授权页启动器、给别人的包）。零基础不用当产品经理补洞。方案没补到能推进之前不算开工。
- **能卖的后半段不要写在本本里当主流程。** 想清后把步骤、依赖、验证和返回动作写回已有工作包，回到直接调用方的当前任务（见 `docs/ENGINEERING-CONTINUITY.md`）；产品主线未完成的授权、打包与交付继续保留。本本不 `init`、不打包、不发 Release。二开不要把有源码线的「可以不接」抄过去当过门。

## 拆成可验证小步

- 每步有"做完怎么算数"的判据；把风险/未知的步骤排前面先拆雷。
- 任何项目动手前先说清文件夹：要留下的（源码 / 当前工作拷贝 / 数据 / 秘密 / 包）和可整夹删除的（只进产品根 `TEMP/`）。各版补丁、界面候选、安装包不进 `TEMP/`。乱了先理，再优化。
- 高风险（一拿到程序就分析、逆向开工具/补丁、接共享授权平台）：按对应技能做 3–4 路互攻，写相反预测；不要让他们复述你的计划再投票。互攻不是停点。干活中间卡住先走 AGENTS「卡住开会」。出口收尾按 `review` skill 走「多步出口」：审完由批评手打报告，写的人不能给自己过。审查不要开子代理。
- 对人先白话。审查轮次再多，也不能说彻底没问题。轻量任务别为规划或审查而规划，直接做更快。

## 和 state 配合

- 阶段/停点交给 `state`，不在这另建一套状态机；规划只是想清楚要往哪走。

## 别假装

- 计划漂亮 ≠ 有进展。
