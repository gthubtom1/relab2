# 项目理解怎样跨过长对话、修改与换人

项目记忆保存工程师对当前项目的理解：谁通过什么过程得到结果、功能为什么存在、现行设计是什么、实现落在哪里、改动会影响谁，还有哪些想法没有决定。它从方案讨论期开始，不等窗口或命令已经完成。记忆帮助 AI 找到应当阅读和验证的材料，不能代替相关代码、业务判断或实际观察。

新项目使用 `feature_set --apply` 与 `map_show`。普通问答、错字和单文件小修不必因此建档。旧记录缺失时，工程方从原话、Git、入口和局部实现恢复，不要求零基础用户重讲产品或填写内部字段。没有记录、旧场找不到、过期或损坏是三种不同的空，不能合成一种，也不能把空模板拷进产品根当成已经恢复。

## 不同事实放在哪里

| 内容| 保存位置| 接手时用途|
|---|---|---|
| 用户说过什么| `OWNER-SPEECH.md` 追加原始事件| 沿来源回读，不拿短摘要覆盖|
| 当前项目理解| `PROJECT-MEMORY.jsonl`；工具生成总图和卡片| 用 `map_show` 分叉查询，不整读日志|
| 当前有效设计| 功能的 `intent/constraints/rationale/sources`| 记录采用的设计与理由，推定须说明依据|
| 已定位实现| `implementation.summary/locations`| 指向接下来应读的源码和消费者，不能当业务已通过|
| 尚未决定的想法| `drafts/questions`，长推演可引用持久设计文档| `--drafts` 按需展开，有价值理由不扔进 TEMP|
| 实际观察与完成| 原有 `state work`、候选与物理收据| `work_ids` 只导航，不另建 done 栏|
| 本次做到哪、返回哪| `WORK-HANDOFF.md` 与 state 调用栈| 指向当前功能和责任，专项后继续原动作|

`MAP.md`、`FEATURES.md`、`features/<稳定ID>.md` 是派生文件，不分别手改。与持久记录不符时，工具报告冲突，运行门不能依据冲突记忆通过。`--render` 重建视图，但不更新材料核对，不生成业务证据。

原始事件和必要工程决定进入 Git。工具在机器侧处理历史，普通查询只输出最新有效视图，AI 不用遍读几万行日志。记录带连续版本和前条摘要以发现意外损坏；它不是抵抗能改全部文件的操作者的安全系统。

## 正常开发中的短循环

1. 接手或压缩后，读交接，核 Git/已有产品状态，再看总图。总图只列第一层和实际使用过程；打开父功能逐层深入。知道名字可直接打开，旧名称仍能找到改名后的 ID。
2. 修改前，读目标分支、依赖与消费者，沿位置读相关代码。设计、源码、来源或依赖改变会显示待核对；不要直接刷新指纹消除提示。
3. 有效设计变化先改 `intent`，实际实现另记 `implementation`。只改按钮位置时，其余文案、数据和失败约束仍保留；有价值但未采用路线放 `drafts`。
4. 根据事实同步说明和位置，列出实际重新读过的 `reviewed` 分支，再验证真实消费者。收据仍由 `state probe` 产生；核对地图不代表业务成功。
5. 交接前处理受影响分支、未决事项和未返回工作，把下一动作写回交接面。按原授权连续推进，不向用户索要内部编号或“继续”。

局部记录可以短，复杂设计链接专门文档。功能如何拆、消费者是否齐全仍须工程判断；字段齐全不能证明想得全面。

## 工程接口

命令由 AI 执行，用户讨论目的、实际取舍和体验。`<hub>` 是中枢根，产品另有根目录；不要在中枢源仓建产品账。

```text
python tools/map_show.py --product <项目根>
python tools/map_show.py --product <项目根> --id <功能ID或名称>
python tools/map_show.py --product <项目根> --search <名字或作用>
python tools/map_show.py --product <项目根> --id <功能> --drafts
python tools/map_show.py --product <项目根> --id <功能> --history
python tools/map_show.py --product <项目根> --check
python tools/feature_set.py --product <项目根> --apply <变更JSON文件>
python tools/feature_set.py --product <项目根> --render
```

`--json` 给自动化消费者，通常配 `--id`。`--check` 非零表示记录需要处理，不是业务验收。历史、草稿按任务读取，不要求固定条数。

首次讨论已有目标时可先写 `project` 和尚无实现的功能，见 [变更示例](../templates/memory-tree/change.example.json)。不要复制示例名字当真实项目。新功能必需 `id/name/purpose/intent`；`implementation` 省略或设 `null` 表示尚无实现记录。计划功能可导航，但不会成为当前实现表的一行。

```json
{
  "expected_revision": 4,
  "reason": "用户调整导出入口；其他约束继续保留，实施后再核对",
  "features": [{"id": "export", "intent": "导出入口位于列表右上方"}]
}
```

同 ID 更新保留省略字段。提供数组则替换该字段，先读当前分支并保留未撤销内容。设计变化不顺手把实现改成已做到，也不刷新核对。`expected_revision` 防止旧记录覆盖新决定；冲突后重读受影响分支，不猜新版本号重试。

`implementation` 需 `summary` 和 `locations`。位置为产品内相对路径，可附 `symbol`；工具只检查符号文字存在，不宣称理解了函数。目录位置把其中文件集合纳入核对，可发现模块新增文件；优先声明相关模块，不把整仓当一个功能的材料。

`sources` 是持久文档路径，可附唯一原文 `anchor`。有锚点时追加别的原话不使该来源失效；重复/丢失锚点则重新定位。外部事实保存来源、版本和观察条件到持久材料；地图不放密钥，不把地图自身当实现或决定来源。

`reviewed: ["export"]` 表示工程方已对照当前设计、实现和声明依赖。工具绑定内容摘要，后续变化会提示重新核对。只改名字、补草稿、重建视图或只核对上游，均不替消费者刷新核对。相同材料不能证明在另一台电脑也运行成功；产品观察仍走候选/环境/断言。

`parent` 仅用于目录，不能成环。`depends_on: [{"id": "storage", "reason": "读取保存的记录供导出使用"}]` 表示实际依赖，允许真实组件间有环。影响沿依赖传到消费者，不限一个邻居；目录相邻不自动等于业务依赖。

改名保持 ID。拆并用旧功能 `replaced_by` 指向新 ID，同一变更接好调用者和父目录。新卡显示前身仍需对账的约束、来源和责任。地图“已替代”不撤回原责任，仍须在 `state work` 按有效决定承接；两个空新功能不能完成旧目标。被替代代码不要求永远留在原位置。

## 旧项目和版本

旧 FEATURES/卡片模式仍能读；单独改 `--now` 现在保留原作用。但旧模式不能识别设计与位置是否过期，会显示边界。新项目默认持久记录，不把旧申报静默升级成已核对事实。

迁移先读旧图、卡片、原话与源码，保存设计、身份和未决问题。人工记录先进入 Git 并移到产品持久历史目录，再建立新记录；工具拒绝覆盖人工地图，不删旧文件“清空重来”。责任账和收据沿用，只有相应观察能升级结论。

`map_freeze` 同时保存当时持久记录和派生文件，使用同一写锁避免混入两个版本。同名不能覆盖，当前记忆变化后旧冻本不能代表当前对照齐备。复制不等于产品可重建或客户已验收，定档仍比较实际前后版本。

## 实际边界

这层可发现声明材料变化、悬空关系、目录环、并发旧写入、损坏记录、派生文件冲突，并保住同一功能未修改字段。它让 AI 从局部入口恢复有效设计。

它不能自动理解所有代码，不能发现未声明模块或未知服务的全部变化。工程方仍要调查新增消费者、运行条件与遗漏需求。地图、物理收据、陌生代理行为分别验证，不能将任一层通过宣传成任意模型以后不犯错。
