# 数据与存储方法

对主人先白话：做到什么、还缺什么、下一步看哪。一次只说一扇窗、一个键。机械项自己跑；主功能给人话清单等人测；做不到当场说。两句不能互相吞掉。迁库只是中途一刀。做完按 WORK-HANDOFF 的方法调用链，回到直接调用方尚未做完的动作；主线的授权、打包与交付要求继续有效（见 `docs/ENGINEERING-CONTINUITY.md` 的当前工作包）。迁移脚本退出 0 ≠ 能回滚。桌面/命令行更新格同样：须见到迁移、备份、回滚，不能只写「回滚」两个字过门。

> 方法在这，阶段目标/该记什么在流程文档 + `state`。

## 一开始就定清楚

- 存什么、存哪（SQLite / JSON / 注册表 / 用户目录）、谁能写（单写入者最省心）。
- schema 带版本号；第一版就想好"以后加字段怎么迁移"。

## 迁移必须能双向验证

- 升级：v1 数据 → 迁移 → v2 能读能用。
- 失败回滚：迁移中断/失败 → 恢复到 v1 且能启动。**迁移前先备份。**
- 用 `state record --kind test` 记迁移/回滚实测（`evidence_level=product|human`）。**不要**占用 `build`：`build.artifact` 只留给安装包/镜像/分发产物，迁移脚本当安装包会把「安装包确认」点绿。

## 别假装

- 备份目录存在 ≠ 能恢复：必须真的恢复一次并复验功能。
- 本机能迁 ≠ 客户老数据能迁：拿真实旧数据测，不是空库。
- 更新不许冲掉 User-owned 的配置/数据/授权。
## 硬门：数据文件存在不是恢复证据

凡是迁移、备份、恢复、升级或回滚，都要用产品真实数据跑一次物理验证，并把结果绑定当前候选/阶段收据。只看到备份文件、迁移命令退出 0、schema 版本变化或测试绿，不能说明用户数据可恢复。

物理检查至少应观察：备份是否可读、恢复后记录数量/关键字段是否一致、应用能否用恢复后的数据继续主流程、失败时是否回到原状态。授权、设备状态、用户配置等 User-owned 数据要与程序文件分开处理，不能为了让安装测试简单而清空或覆盖。探针配置和收据不能包含真实秘密。

恢复后还必须复验业务；文件回来了但程序打不开、数据关系断了或权限丢了，都算失败并回到受影响阶段。
