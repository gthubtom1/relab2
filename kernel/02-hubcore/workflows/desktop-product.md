# 原创桌面产品流程

施工、换技能和交接时，按 `docs/ENGINEERING-CONTINUITY.md` 把原话、有效决定、最终消费者、影响面、真实观察与返回动作接到已有工作包。只展开当前这一项；材料有字不算完成。

## 怎么用这份文档

阶段清单、停点、进度真源都在 `state`，不在这份散文里。对主人先白话：做到什么、还缺什么、下一步看哪。一次只说一扇窗、一个键。机械项自己跑；主功能给人话清单等人测；做不到当场说。两句不能互相吞掉。**轻量不要走本流程、不要 init。以后要卖不要收成直接写代码、写页面。无产品账不要对当前工作区跑 status。方案能推进、产品夹不在中枢里面之后再 init。**

```
python tools/state.py status  --product <产品目录>
python tools/state.py confirm --product <产品目录> --stop-point "<停点名>" --evidence "这一步验证了什么（具体可复核）"
python tools/state.py record  --product <产品目录> --kind spec|arch|module|build|follow|cover|replay-order --data '<json>'
python tools/state.py candidate --product <产品目录> --set <当前构建> [--bless]
```

> Windows / PowerShell 传内嵌引号的 JSON 容易被吞——复杂 JSON 用 `--data-file <文件>`（BOM 也能读）。

阶段是数据，见 `templates/desktop-product.phases.json`（已知产品线的默认阶段 id、顺序和物理检查不可删、改名或重排；可增加步骤并按业务适配实现）。每个停点都有 `requires`：没记对应制品，`confirm` 过不了。不要套二开停点；能交给别人用必须有 `build`（包内主程序 = 刚验的候选哈希）。

**不算（防换皮，未用真产品打穿）：** 测试绿 ≠ 主业务；开发机 ≠ 干净机；另装文件夹 ≠ 覆盖更新；窗口起来 ≠ 核心功能做成。架构确认禁止只交一句 `decision` 把「怎么交给别人用 / 写动作在哪 / 还没测的环境」一口吞掉；工程问题先查现有实现与可行方案；确实缺业务取舍时，给推荐和理由再问主人。缺证据不能 confirm，不要把 SKIP/未决写进 arch。机器：架构须写动作+分发才能点绿；这格不能 SKIP 点绿。实现格写动作未证不能点绿。空成功只拦表里金句、按停点中文名；未入表的格不拦。未用真产品打穿，不算五类都能管。「不要跳过」不算裁剪。

spec 须 `acceptance`；arch 须 `decision`；实现/首次启动/更新/交付的 test 须 `evidence_level=product|human`。构建候选须 `--bless`。边做边留下以后还能用的记录（`record --kind anchor`）；还在做不拦，要点「做成了、进下一阶段」时账本里必须已有这些记录。

## 开场先讨论，后面和二开同一套卖路（只换前面，仍抱本书，不要换成 exe-rebuild）

用户只说了一句简单需求：禁止立刻写代码，也不要先画窗口。先用人话把方案补全：这个项目怎么做、要哪些功能、什么组件、怎么衔接、失败怎么办、数据放哪、缺什么、以后怎么卖。常见坑你挡住，不要主人当产品经理补洞。方案没补到「可以一步步推进」之前不算开工，也不要把「进度更新」当成开写许可。卖路径别丢；该换书仍要换，不要把「只加载本 skill」读成整场不换书。

改功能时：先读已经记下的 spec / arch / module 和现有界面；改 A 之后复验 B 还在、加过的组件没被拿掉。靠项目账，不靠聊天记忆。

主流程能用之后走**后半段**（和二开同一套，前面是从零写，不是逆向）。不要直接跳到安装包。先改界面，再**问**主人接不接自己的授权。可以不接——把「这场不接」写进 spec/arch，走改界面 + 打包；不要为过关硬接。若接，把「接自己的授权」写进 spec/arch。spec/arch 里没有这两句之一，就不要开始打安装包。开场或架构格里的「不接」不能当已问。不要用 confirm 的 SKIP 去点绿「需求合同确认」或「安装包确认」；这场不接不是 SKIP。「不要抄二开」不是砍掉这一问，也不是扔掉授权页。若接：授权平台 → 授权页（验卡密）→ 软件主页面。先把通用授权页改成这个产品的样子（主人看过这一页；不要另写一套协议、不要改授权平台、不要拿没改过的通用页直接接正式）→ 三种基础真跑（卡密对且没过期才开后面的程序；不对或一进来就过期则不开；用到一半到期则关掉后面的程序并且授权页自己也关。作废/断网按这场要不要测，不是每场必测）。还要第四种：卡仍有效，但这台 `DEVICE_NOT_BOUND` / 被挤掉 / 已解绑时必须停主程序。开着还要周期性 verify，只 activate 不算；一句「激活/验证/解绑都要」不够。两套钟不准改混：到期靠 expires_at 本地关，不要改成到期也必须再问才关。挤机必须再 verify，下一次验证内停。expiry 是卡还剩多久，禁止把验证间隔/cache_until/next_verify_at/20 秒/60 秒交给核心或标题栏。测试/验收间隔默认 60 秒，不要 20 秒硬刷。只有一台时超过验证间隔还在，没人挤不会自己关。RATE_LIMITED 不是停机。宽限不是多台同时登录；最大设备数已售不跟，挤机开关已售跟着变。藏页/关页是附加（页藏后台、人关软件页也关），不能拿来交差，不能顶第一种。购买/联系/更新一次做全：购买网址和联系字跟这张卡的下游，原文原样，空则点了没反应、不加「QQ」、不准自己编；更新带版本号问平台，有新版才提示，点了打开网盘；设备码 `缩写-XXXX-XXXX-XXXX-XXXX`；激活后还要周期性验证、解绑后停；测试只用 `ceshi1`、新发卡；已售卡锁快照；软件侧交对接文档，平台侧只登记。人能看见主功能那天锁清单+总图+改动图当**原创基线**，一版一个 `work/vX`，发出去冻进 `freeze/vX`。→ 先在测试环境测通，再连正式自己的平台（先测再连正式；共享平台先孪生）。接了授权后对人测两段：先只有一台、等过验证间隔还开着（没人挤不会自己关）；再第二台挤第一台，第一台下一次验证内停（被挤掉会停）。再打包。登录（谁能进系统）和收费授权（要不要自己的卡密）是两件事，对人分两句问。开场一次只问一件能看见的事，不要一次丢三件。

不要抄的是逆向、把没源码的核心当载荷再套一层、挡对方授权页、产品怎么分三选一、把二开 `record --kind license` 抄过来交差。**要抄的是后半段整段、授权页验卡密、授权 A 全表、清单地图冻本、一版一目录。** 不要把「不要抄二开」读成扔掉授权页。开场不要拷功能表、不要建档案夹给主人签字。已有表则开工先 `python tools/map_show.py --product <产品>`（不要 `--id`），改哪再 `--id`。禁止整仓重读。可以不接授权。若接了，有窗才改授权页样子，主人看过再测藏页关页。先测再连正式。

**还没答完不准开工。** 部长自己答，不准印给主人当考卷，不准每格把十四问全问一遍。不要抄二开「原件接/关/替」。

- 主界面人看见什么？
- 失败时人看见什么？
- 数据放哪？坏了怎么回去？
- 清单从哪天写？

## 四条贯穿所有阶段的纪律（都是从你真实翻车、借二开那套过来的）

1. **一版一个工作目录，git 定档还要，构建以 candidate 为准。** 真实教训：本地一堆无名副本，改错文件。→ 这一版只在 `work/vX` 里改；下一版新开 `work/vY`，不要在同一盘文件上闷头叠。功能定档仍认 git（A 测好提交后再做 B）；当前构建/发布候选用 `state candidate --set` 登记。`--bless` 只备份打好的包，磁盘只留最新一份，不能当功能相册。一块功能主人测好了就提醒定档；下一刀只改最新定档之后的当前文件，不要凭聊天里的旧代码重写。乱堆的无名副本仍禁止。解包/日志/草稿只进产品根 `TEMP/`；`work/vX`、冻本、功能表不进 `TEMP/`。
2. **需求先补全再动手；新需求先记再做。** 真实教训：做到一半发现最初需求漏了权限/异常/空数据/性能，推倒重来。→ 阶段 0 用清单把这些逼出来；中途冒出的新需求先 `state record --kind spec` 记进清单并重新确认，别直接开写——那正是范围漂移和推倒重来的根源。（DEC-04）
3. **架构决定和已有模块要记账，实现前先读。** 真实教训：长对话后 AI 忘了架构决定、或重复造了已经有的模块。→ 架构决定 `state record --kind arch`、已有模块 `state record --kind module` 记进 manifest；每次开始实现前先读它们（`state status` 会提示你有多少条），别凭记忆、别重造轮子。
4. **同源制品链。** 代码 → 测试 → 构建候选 → 发布候选 → 包内主程序 → 安装后主程序，分别登记源码、构建产物和包的身份与转换关系；包内与安装后的同一主程序比较哈希，不要求源码和安装包哈希相同。别"验 A 发 B"。用 `state record --kind build` 记这条链。

## 阶段 0 · 需求与验收　→ 停点「需求合同确认」
- **用户该看到**：受众、痛点、核心主流程、可观察成功标准，写成需求合同。还要看见后面怎么卖（改界面 → 问接不接自己的授权 → 打包），**本格不要当面逼答卡密**。
- **做**：先讨论再记。除了功能，**逐项过一遍最容易漏的**：谁能进系统（登录/权限，不是收费）、异常/错误流、空数据/首次使用、性能、数据来源/备份/迁移/删除、上线后更新与售后。**接不接自己的收费授权等到核心能用、改完界面之后当面问**，不要提前到本格，没问不能当成已经问过，也不能拦本格 confirm。用 `state record --kind spec` 把需求合同记下来。
- **别假装**：聊天里"我理解了" ≠ 需求确认；只列功能、不问上面那几项 = 埋下"做到一半推倒重来"的雷。一句话直接开写 = 没做到零基础那条。

## 阶段 1 · 架构与地基　→ 停点「架构确认」
- **做**：定架构、数据 schema、UI 骨架、安全地基；建 Git 基线。**关键架构决定 `state record --kind arch`、计划/已有的模块 `state record --kind module` 记下来**（谁负责什么，避免以后重造）。
- **别假装**：目录建好 ≠ 能跑。

## 阶段 2 · 分阶段实现　→ 停点「核心功能实现确认」
- **做**：**动手前先读 manifest 的 arch / module**（别重造已有模块、别违背已定架构）；小步实现 + 相关测试 + 真实主流程真跑；每产出一个可跑构建就 `state candidate --set` 登记。冒出新需求先 `record --kind spec` 再做。**每改完一刀，复验旧功能还在、加过的界面组件没被拿掉。** 记过的模块名必须写进本格 test，机器才认复验过。一块功能主人测好了就提醒定档（git 提交），再开下一功能。核心能用之后先改界面并当面问接不接自己的授权，不要提前到需求格，不要直接进构建/安装包格。人能看见主界面那天，部长自己写下功能名和**作用是什么**，并锁**原创基线**（清单 + 总图 + 改动图 + 这一版 `work/vX`）。空表不得说完善。旧场表空：先从 Git、源码、交接、原话和实际候选恢复，标清仅源码推定与仍待运行的部分；只问无法恢复的业务决定。不要先建档案夹。
- **别假装**：单元测试绿 ≠ 主业务成功。改了新功能、旧组件没了 = 没挡住通病。模块表在、测试没点名 = 没读表。

## 阶段 3 · 构建候选　→ 停点「构建候选确认」（requires: candidate，且必须 --bless）
- **没答句就停：** 核心能用、改完界面之后当面问的答句须已写入 spec/arch。开场或架构格不算已问。没有就不要点「构建候选确认」，不要 `record --kind build` 打 zip，不要 `gh release`。
- **若接了就停：** 答句是「接自己的授权」时，本格不要打 zip，除非已按形态看见三种基础，并且按顺序看见：先没人挤不会自己关，再被挤掉也停；购买/联系/更新也看见了。不接仍可打。
- **没看见就停：** 本格测试结果「做成了什么」里要写清：主人已经看过换成这个产品的界面（写看见了什么、主流程还在不在）。只写计划或看起来不算。记录实际看到的对象、行为和对应版本；标点或换一种说法不能制造观察证据。不要只写证据栏。不要把短句当完成口令抄进测试结果。没有看见就不能点「构建候选确认」。
- **做**：构建出与源码同源的候选，落哈希，`state candidate --set <候选> --bless` 记为 last-good。
- **别假装**：能编译 ≠ 能安装；status 催你改界面再问 ≠ 你可以先点构建。

## 阶段 4 · 安装包　→ 停点「安装包确认」
- **没答句就停：** spec/arch 里须有主人当面写下的「接自己的授权」或「这场不接」。没有就不要打安装包，不要 confirm「安装包确认」。开场或架构格里的「不接」不能当已问。若接：通用授权页已改成这个产品的样子（主人看过）且三种基础加第四种真跑（对才开；错不开；用到一半到期关掉程序和授权页；卡还没到期但这台被挤掉/`DEVICE_NOT_BOUND` 也停。作废/断网按这场要不要测，不是每场必测）。购买/联系/更新也要一次做全（跟下游原文、空则点了没反应、更新带版本号问平台有新版才打开网盘）。confirm 证据须含主人看过这张授权页、从这页进了主页面、这三种基础（含用到一半）、被挤掉会停、没人挤不会自己关、开着还在周期性验证，以及购买/联系/更新；三种基础不能代替授权页，也不能单独点绿。一句「激活/验证/解绑都要」不算第四种。RATE_LIMITED 不是停机。藏页/关页是附加，不能顶第一种。还须一段未连正式的孪生/测试分身/先测，另记已连正式；一句「先测再连正式」不算。这场不接不套三种基础。本格起产品根须已有原创基线（清单+总图+改动图+这一版 `work/vX`）；发版冻进 `freeze/vX`。
- **做**：做安装包/签名；数据 schema、迁移、备份策略可以一起设计，但本格 `record --kind build` 只记**安装包**（磁盘上的包文件 + 当前候选哈希）。本格起产品根 `FEATURES.md` 须有真实行（功能名+作用），并有定档冻本对照；空表头不算记得。迁移/回滚实测留到更新格用 `test`，不要把脚本/配方文件当成 `build.artifact`。
- **别假装**：包生成了 ≠ 装得上。

## 阶段 5 · 干净安装与首次启动　→ 停点「首次启动验收确认」
- **做**：在干净环境真跑 clean install + 首次启动；最终客户无需开发环境即可使用。对着刚打的那份包哈希，不要换一份没打包的候选再点这一格。
- **别假装**：本机能跑 ≠ 客户机能装能启（真实教训：本机好好的，客户装不上 / 一启动就崩）。

## 阶段 6 · v1→v2 更新与回滚　→ 停点「更新回滚演练确认」（requires: build + 本阶段新 test + follow + cover）
- **没答句就停：** 和安装包同一条。打包格写了「这场不接」，本格改口「接自己的授权」仍要两段，不能只改口过门。
- **做**：真跑 v1→v2 升级、数据迁移、以及迁移失败后的回滚 + 回滚后再次启动。必须是已装软件里点更新，不是开发机再装一次。接了社区授权平台时：带当前版本号问平台，有新版才提示，点了打开网盘网址，就是客户路径，不是冒充。半成品不准放到客户会下到的地址。定档冻本对照上一份原创基线的位置。先 `state record --kind follow` 写下三句：我们改过哪些、这一版新改了什么、哪些还能认哪些是新门。另 `state record --kind cover` 记下客户路径（已装软件里点更新，覆盖安装盖成同一软件）；本项 SKIP、吃新上游不能顶客户点更新。变动少按清单再核对，架构大变就重做，不许照抄。没有这三句和客户路径不能点更新回滚确认。`replay-order` 不是更新正路，禁止拿旧脚本或重放顺序交差。**更新不能冲掉用户的配置/数据/授权**（保留 User-owned）。`build` 只记 v2 安装包；迁移/回滚实测记 `test`。不要把迁移脚本记成 `build.artifact`。
- **别假装**：备份目录存在 ≠ 能恢复；回滚必须复验功能，不只是文件回来了。开发机再装一次 ≠ 客户已装那一份升了。

## 阶段 7 · 交付与验收　→ 停点「交付验收确认」（requires: build + 本阶段新 test）
- **没答句就停：** 和安装包同一条。前面写了「这场不接」，本格改口「接自己的授权」仍要两段。授权测试与更新演练分别留实际观察；测试环境验证、正式接线是两段不同事实，未执行就保留未完成，不能靠措辞过门。
- **做**：把安装包 / 使用说明 / 回滚预案真正**交到用户手上**；用户在**真实环境**跑通一次核心主流程并**明确点头验收**。冻本和功能表必须还对得上这一版，不能只交一个包。当前候选必须仍是更新格那份 v2 包哈希，不能退回 v1 或另换没更新过的字节去交货。交付结论同时列**已验证 / 未验证 / 残余风险**，让第三方能独立接手。`state record --kind build` 记最终交付物哈希。
- **别假装**：前面阶段全确认 ≠ 已交付。"机器显示全部完成"但从没有一步在确认"东西真到了用户手里、被接受了"——那正是"防假完成"要堵的最后一个缺口。所以本阶段的停点专收这一环。

## 交付出口

最终结论同时列：已验证、未验证、残余风险，以及"从哪看起 / 怎么验 / 怎么回退 / 唯一下一步"，让第三方能独立接手。
高风险交差前换加载 `review`（一次一本）：按四审帽子走完（程序→产品→测试→发布），写的人不能给自己过，也不能自己宣布完成。`state` 全绿不是完成。
交付后再改同一产品：用 `state reopen` 从受影响阶段重开，清单还是这份 `.hub`，不要 `init` 当新项目，也不要走整条线只改错别字。更新演练在合同第 6 格（本线「更新回滚演练确认」），不是再开一份合同。
## 硬门：桌面产品必须真实运行，不接受“窗口亮了”

实现、打包、干净安装、更新回滚和交付阶段都要按合同的 `physical_checks` 运行 `state probe`。没有当前候选的物理收据，`confirm`、`record --kind build` 和 release gate 都必须停。测试绿、窗口出现、退出码 0、文件存在和模型文字不能单独证明桌面主流程成功。机器没看成、超时、误判、探针没跑起来、红探针其实已经通过、或控不了电脑时，主人亲手测过这一项后用白话说看见了什么；由工程方 `state accept-seen --check <检查 id> --quote "主人看见了什么"` 登记，再跑该探针。不要把 python 命令甩给主人。不要写「符合要求」，也不要一句话跳过全部机器门。硬编码 365 天不能洗白。

- **探针先行与防丢清单**：涉及界面交互、数据持久化与主流程改动前，先在 `.hub/physical-gates.json` 配置机器断言并在会话中列出防丢清单。施工中严禁以局部语言单测通过向主人宣称做好了；单元测试必须在临时沙箱目录运行，严禁读写或污染用户真实的生产配置路径。
- `business_flow` 要驱动真实用户主流程并观察结果，不是只启动窗口。
- `package_install` 要对真实安装包做安装，不是看 `MZ` 或文件大小。
- `clean_install` 要在干净环境首次启动并完成主流程；`update_rollback` 要升级、失败回退、回退后再次跑主流程；`handoff` 要验证交接资料和实际可复现步骤。
- 若接了自己的授权，打包及之后的格还要 `license_dataflow` 机器观察卡还剩多久（不是 20 秒/60 秒间隔，也不是 next_verify_at）、用到一半真卡过期停、被挤掉停、只有一台超过验证间隔还在、RATE_LIMITED 不是停、周期性 verify；须在 `.hub/physical-gates.json` 里配置。这场不接不套。
- 网络必须在 UI 线程之外运行，错误回到产品自己的横幅/状态区；不要用系统 MessageBox 倾倒原始 JSON。

主人没有真实看见并点头验收前，不调用打包器、发布器或上传命令。`state gate` 不能阻止任意终端命令，所以账外产物必须标为未验证，不得包装成正式候选。
