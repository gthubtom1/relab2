# 九个必测场景：测什么、为什么这么测、判定标准是什么

> 全套 **1 – 9**，一条不留。
>
> 被测对象：`work/context-isolation/ctxiso/`（只读，一行没改）
> 被测产品：`D:\临时项目\hub-dock`（只读）
> 假产品：全部建在 `05-tests/TEMP/`，跑完整个目录删掉

## 跑法

```powershell
cd D:\临时项目\hub-dock\work\context-isolation\05-tests
python run_all.py
```

| 退出码 | 意思 |
|---|---|
| 0 | 6 个场景全绿 |
| 3 | 有红项（断言没过，或真仓库被改了） |
| 2 | 环境没准备好（找不到账本 / ctxiso 起不来 / 没有真 state.py） |

常用参数：

| 参数 | 作用 |
|---|---|
| `--only 3,7` | 只跑指定场景 |
| `--keep-temp` | 跑完保留 `TEMP/`，方便翻假产品 |
| `--keep-state` | 跑完保留侧车状态目录里本轮假产品那几格 |
| `--no-write-result` | 不刷新 `RESULT.md` 的自动段 |

只依赖 Python 3.12 标准库。跑的时候会调真实 CLI（`python -m ctxiso …`）和真实的
`hub/tools/state.py`，不用 mock——要测的就是它们真跑出来的字节。

## 三条共通的判定纪律

**一、不断言"跑通了"，只断言可数的数字或可查的字符串。**
每条断言要么是一个门槛（`bytes <= 6000`、`< 2000 B`、`< 15 s`），要么是
"某个正文片段一个都不许出现在输出里"。没有"输出看起来对"这种判法。

**二、"没有泄漏"用 shingle 比对，不靠肉眼。**
把源文件切成连续 30 字（账本用 60 字 / 50 字）的片段集合，再去输出里找。
找到一个就算红。这样"泄漏了 3 个字"也逃不掉。首行要单独排除——
首行是索引里**合法**的一行用途（`store._first_line` 就是这么取的），不是正文外泄。

**三、真仓库零改动是机器证明的，不是承诺。**
`run_all.py` 跑前跑后各取一次指纹（大小 + 纳秒 mtime），逐文件比对。

- **硬保护区**（任何新增/改动/消失都直接判红）：`hub/`、`.hub/`、`features/`、
  `work/v0.1.0/`、`02-hubcore/`、`ctxiso/`，以及仓根所有文件。
- **软保护区**（只报、不算红）：`00-ANALYSIS/`、`01-design/`、`03-bundle/`、
  `04-console/`、`03-tests/`。依据 `SPEC-自包含安装.md` §2 的文件分区表，
  这几个目录分别归 E（T5）和 A/B（T1/T2），他们同时在开工——
  第一次跑的时候把 `00-ANALYSIS/` 误列进硬保护区，T5 写文档就误报了一次红，
  已按分区表改正。

所有子进程都带 `PYTHONDONTWRITEBYTECODE=1`——不然 `python -m ctxiso` 会在
`ctxiso/__pycache__/`、`hub/tools/__pycache__/` 里写 `.pyc`，那也是改动受保护区。

## 场景 1　普通新任务

**测什么**：主人随口提一句新活的时候，任务包里不会因为仓里堆了历史就自动塞一大片东西进来。

**为什么这么测**：真仓库的污染源是现成的——`.hub/ledger.jsonl` 26 MB / 1118 条事件，
`OWNER-SPEECH.md` 73 KB / 473 行，`CHANGES.md` 151 KB / 1486 行。
拿真数据测才有意义，造假数据测不出"到底漏了多少"。

**怎么做**：

```
python -m ctxiso pack --product D:\临时项目\hub-dock --intent "给主人解释载入流程" --stage 0-spec --json
```

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 1.1 | pack 成功 | rc = 0 |
| 1.2 | 预算硬顶 | `bytes <= 6000`（读 `ctxiso/config.json` 的 `pack_budget_bytes`，不写死） |
| 1.3 | 包自报的 budget 与配置一致 | 两者相等 |
| 1.4 | 无 OWNER-SPEECH / CHANGES 正文 | 两个文件各切 30 字 shingle，命中数 = 0（首行除外） |
| 1.5 | 出现的是索引行 | 包里有 `路径｜大小 B｜行数 行｜一行用途` 这种行，且两个文件名都在 |
| 1.6 | 一行用途确实来自首行 | 索引里的用途字段能在文件首行里对上 |
| 1.7 | `omitted` 写清没展开什么 + 怎么取 | `omitted` 非空，且里面出现 `ctxiso query` / `archive list` / `read` 之一的取回命令 |
| 1.8 | 【本包刻意不含】段存在 | 该段必须在 |
| 1.9 | 无账本事件正文 | 从 26 MB 账本均匀抽 217 条长事件、切 60 字片段，命中数 = 0 |
| 1.10 | 无 observed/assertions JSON 键 | 带引号的 `"observed"` / `"assertions"` 等一个都不许出现 |

> 1.10 特意查**带引号的**键名：`【本包刻意不含】`那段说明文字里本来就有一句
> "observed/assertions 原文"，那是给人看的说明，不是收据正文，按字面查会误判。

## 场景 2　连续任务

**测什么**：这一轮跑完，下一轮的任务包不会把上一轮的东西带回来。

**为什么这么测**：累积回灌是"上下文越用越脏"的主要来源。单看一次 pack 没问题，
连着跑两次才发现第二包比第一包胖——所以这里连着跑两次同一产品、只换 intent。

**怎么做**：连着两次 `pack`，intent 分别是
`"给主人解释载入流程"` 和 `"查清 state status 为什么会回灌历史缺口"`，stage 都是 `0-spec`。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 2.1 / 2.2 | 两次的【任务意图】行各自正确 | 意图原文在对应那行里 |
| 2.3 | 互不串 | 包 1 不含意图 2，包 2 不含意图 1 |
| 2.3b | 只有一个意图行 | 每包 `【任务意图】` 恰好出现 1 次 |
| 2.4 | 大小之差 | `abs(bytes1 - bytes2) < 3000`（预算的一半） |
| 2.5 | 都在预算内 | 两次都 `<= 6000` |
| 2.6 | **除意图行外逐字节相同** | 去掉【任务意图】那一行后，两个包完全一样 |
| 2.7 | 索引没被重灌 | 两次 `indexed_events` 相等 |

2.6 是这一场景最硬的一条：只要第二包多出一个字节，字符串就不相等，直接红。

## 场景 3　自动记录

**测什么**：做了这一套隔离之后，中枢原来那 8 个自动记录器还在照常写，一个都没被关掉。

**为什么这么测**：这是最容易"顺手关掉"的一层——为了少读点东西，很自然地就把
记录关了。所以不能只看 `observe check` 说好，要**真的用真工具写一刀**再看它变没变大。

**怎么做**：

1. `ctxiso observe recorders` 看 8 项清单。
2. 在 `TEMP/fake-auto/` 建一个**假产品**，用**真的** `hub/tools/state.py` 跑完整流程：
   `init → plan → require --append → work --define → work --enter → work --leave → record`。
3. `ctxiso observe snapshot`（此时账本、原话账已经在了，才能观测到"变大"）。
4. 再制造一次追加：再跑一次 `require --append` 和 `work --enter`，并往假产品的
   `OWNER-SPEECH.md`、`CHANGES.md` 各追加一行。
5. `ctxiso observe check`。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 3.1 | 8 个记录器都在 | 清单恰好 8 项，缺一即红 |
| 3.2 | 策略写明一律保留 | `policy` 含"一律保留" |
| 3.3 | 真 state.py 流程跑通 | 7 步全部 rc = 0 |
| 3.4 | 账本被真的追加 | `.hub/ledger.jsonl` 非空 |
| 3.5 | 原话账被真的追加 | `.hub/requirements.jsonl` 非空 |
| 3.6 | 快照覆盖到被观测文件 | 指纹 ≥ 5 个文件 |
| 3.7 | 追加动作真写进去了 | 第二轮 `require` / `work --enter` 都 rc = 0 |
| 3.8 / 3.8b | `observe check` | `ok == true` 且退出码 0 |
| 3.9 / 3.10 | 没变小、没消失 | `shrank == []`、`gone == []` |
| 3.11 | 至少一条 grew | `len(grew) >= 1` |
| 3.12 | 没有 new | `new == []`（说明快照时就都在，测的是"变大"不是"新出现"） |
| 3.13 | 账本是纯追加 | 同一个 `work_enter` 事件出现 2 次，进两次都留着 |

**绝对不许往真仓库 `.hub/` 写测试数据。** 假产品建在 `TEMP/fake-auto/`，
`state.py` 的 `--product` 一律指向它；保护区指纹会把真 `.hub/` 的 7 个文件一起验。

## 场景 4　历史查询

**测什么**：主人明确说"我要看过去那份资料"的时候，能找到位置、按意图取到正文，而且
**没意图的时候一定拿不到**。

**为什么这么测**："知道存在 ≠ 读正文"这条规则如果只在提示词里写、工具里没兜住，
一次误操作就把 151 KB 改动图倒回上下文。所以拒绝路径和放行路径都要测，缺一不可。

**怎么做**：在 `TEMP/fake-hist/` 造一份 v1 规格、一份 v2 规格和一份 60 句的原话流水，
先 `ctxiso index`，然后跑 `archive list` / `read` / `compare`。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 4.1 | `archive list` 无正文 | 3 个源文件切出的 1820 个 30 字 shingle，命中 0 |
| 4.1b | 最长命中正文行 = 0 | 源文件里没有任何一整行出现在返回体里 |
| 4.1c | 返回体远小于源 | `len(返回体) < 源总量 / 4` |
| 4.2 | 找得到 | 三份资料的路径都在索引里 |
| 4.3 | 只有元数据字段 | 每行字段 ⊆ {path, kind, size, mtime, lines, sha, one_line} |
| 4.4 / 4.4b | **不带 `--intent` 被拒** | 退出码 = 2 且 `refused` 为真 |
| 4.4c | 拒绝时不给正文 | 拒绝体里没有 `ok: true` |
| 4.5 | `read --intent` 成功 | rc = 0 |
| 4.5b | 正文回来了 | 返回的 `text` 非空 |
| 4.6 | 留了收据 | `reads.jsonl` 里有 `target` / `intent` / `bytes_read` / `sha8` |
| 4.7 | `compare --intent` 成功 | rc = 0 |
| 4.7b | 只回差异摘要 | 返回里有 `added` / `removed` / `similarity` / `hunks` |
| 4.7c | 不回两份全文 | 两版规格的 1461 个 shingle，命中 0 |
| 4.7d | 返回体远小于全文 | `len(返回体) < 两份全文 / 4` |
| 4.8 | 越界读取被拒 | `--target ../../OWNER-SPEECH.md` 退出码 2、`refused` 为真 |

> 4.5 / 4.6 当前是红的。原因见 `RESULT.md` 手写分析：**`ctxiso/archive.py:118`
> 用了 `hashlib.sha8`，标准库没有这个算法，`read --intent` 必崩。**
> 断言没有为了让测试变绿而放宽；崩了就记红。

## 场景 6　上下文压缩

**测什么**：上下文被压缩以后，活下来的是当前任务的 7 个字段，历史整包留在盘上、
只留取回指针。

**为什么这么测**：宿主自己压缩的时候会把"当时上下文里的一切"重新总结一遍，
历史于是被二次固化。要证明这条路被堵死，光看 SURVIVOR.md 有几行不够——
必须在**历史很大**的条件下证明它没被带回去。

**怎么做**：

1. `compact --contract-only` 对着真仓库跑（纯读配置，不写任何东西）。
2. `TEMP/fake-compact/` 造一个 **800 条事件 / 2.78 MB 账本**的假产品，索引后
   `compact --state '{…}'`。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 6.1 | 存活字段正好 7 个 | 与配置里的 7 个字段逐个相同 |
| 6.2 | 规则写明历史正文不进摘要 | 规则里出现"不进入压缩摘要" |
| 6.3 | 规则写明丢掉的是指针 | 规则里出现"按指针取回" |
| 6.4 | 规则写明取回要带意图 | 规则里出现"读取意图" |
| 6.4b | 没有规则要求重新总结历史 | 没有任何一条规则肯定式地要求重述历史 |
| 6.5 | 假产品历史已索引 | 800 条进索引 |
| 6.6 / 6.6b | 生成 `SURVIVOR.md` 与 `dropped.json` | 两个文件都存在 |
| 6.7 | 存活集 = 传进去的 7 个字段 | 相等 |
| 6.8 | `SURVIVOR.md` < 2000 字节 | 硬门槛 |
| 6.9 | 不含探针名 / 事件 kind | 12 个已知名（`core_entry`、`physical_probe`…）命中 0 |
| 6.9b | 不含 OWNER-SPEECH / CHANGES 内容 | 1836 个 shingle，命中 0 |
| 6.9c | 不含账本事件正文 | 200 条事件切 50 字片段，命中 0 |
| 6.9d | 不含账本事件时间戳 | 账本里的 ts 一个都不许出现在 SURVIVOR.md |
| 6.10 | `dropped.json` 每项都带 what/count/how | 结构检查 |
| 6.10b | `dropped.json` 里没有正文 | 1836 个 shingle，命中 0 |
| 6.11 | 账本那项带取回命令 | `how` 里含 `ctxiso query --kind <kind> --limit 50` |
| 6.12 | 资料那项带取回命令 | `how` 里含 `archive list` 和 `read --intent` |
| 6.13 | `dropped.json` 体积很小 | `< 4000` 字节 |

> 6.9d 特意只查**账本里的** ts。`SURVIVOR.md` 第一行有一句"生成：<ISO 时间戳>"，
> 那是本次生成的出处，不属于历史回流。第一版断言写成"不许有任何 ISO 时间戳"，
> 把这句合法的话也判红了——是断言写错，不是代码错，已改。

> `--state` 这一半故意跑在假产品上：真仓库的侧车状态目录是统筹在用的，
> 没必要往里塞我造的 800 条假事件的 SURVIVOR.md。历史照样是 800 条 / 2.78 MB，
> "压缩后不回流"这条该证明的照样证了。

## 场景 7　大量历史文件

**测什么**：历史资料从 100 份涨到 2000 份，每次任务看到的上下文**一点不变胖**。

**为什么这么测**：场景 1 只证明了一次包不大。真正会出事的是"时间久了"——
文件数涨一个数量级，如果 pack 是 O(文件数) 的，增长就会直接砸进上下文。
所以必须做**两个规模**的对照，只看一个规模说明不了问题。

**怎么做**：造两个假产品，`fake-big`（2000 个 4 KB 文件 = 8.2 MB + 5000 条事件 / 16.4 MB 账本）
和 `fake-small`（100 个 4 KB 文件 + 同样 5000 条事件的账本）。两个都 `index`，都 `pack`。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 7.0 | 假产品造好了 | 2000+ 文件，账本 ≥ 2 MB |
| 7.1 | `index` 耗时 | `< 15000 ms`（整条命令，含解释器启动） |
| 7.2 | 索引库远小于源 | `index.sqlite / 源总量 < 0.10`，并报出实际比值 |
| 7.3 | doc 表真有 2000 行 | `doc_kinds.history == 2000` |
| 7.3b | 对照产品也索引好了 | `fake-small` 也要先 index（pack 只读索引库，不自己扫目录） |
| 7.4 / 7.4b | 两个规模都 `bytes <= 6000` | 预算硬顶 |
| 7.4c | 索引行数一样多 | 两个包列出的索引行数相等，比较才公平 |
| 7.5 | 索引行数 ≤ `pack_max_index_rows` × 类别数 | 10 × 3 = 30 |
| 7.6 | 其余进 `omitted` | `omitted` 里写明未列份数 + `archive list --kind history` |
| 7.6b | `omitted` 里的份数算得对 | 期望 1990 份未列 |
| 7.7 | **包大小不随文件数增长** | `abs(bytes_2000 - bytes_100) < 500` |
| 7.8 | 第二次 index 是增量 | 账本 `read_bytes == 0` |
| 7.8b | 没有新事件 | `new_events == 0` |

> 7.6b 当前是红的。原因见 `RESULT.md` 手写分析：
> `ctxiso/pack.py:49` 写的是 `store.docs(con, limit=500)`，
> 所以 doc 超过 500 份之后，`omitted` 里的"还有 N 份未列"按 500 算，
> 2000 份时它说"还有 490 份"，实际是 1990 份。

**跑完删掉**：`TEMP/` 整个目录（`--keep-temp` 可留），
以及侧车状态目录里本轮假产品那几格（`--keep-state` 可留）。

## 场景 5　项目更新

**测什么**：第二版来了，能对比第二版与之前记录的第一版资料，快速定位改了什么。

**为什么这么测**：`compare` 是"历史资料唯一允许被拿出来看"的通道。
它一旦退化成"回两份全文"，就等于给上下文开了个后门——而这个后门平时看不出来，
只有差异很小时才明显。所以差异要造得**小到能手算**。

**怎么做**：`TEMP/fake-update/` 里造四组版本资料，差异覆盖四种：

| 组 | 差异 | 期望 |
|---|---|---|
| a-modify | 改一行（F3 打印 → F3 打印与传真） | `added=1 removed=1`，1 个 `replace` |
| b-append | 加一行（F6 移动端） | `added=1 removed=0`，1 个 `insert` |
| c-remove | 删一行（F5 审计） | `added=0 removed=1`，1 个 `delete` |
| d-reorder | 整块搬移（F7 从末尾挪到第 3 行） | `added == removed > 0`，行多重集不变 |

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 5.1 / 5.1b | 不带 `--intent` 被拒 | 退出码 2 且 `refused` 为真 |
| 5.2 | 纯改 | `added=1 removed=1 hunks=1` |
| 5.3 | 纯加 | `added=1 removed=0` |
| 5.4 | 纯删 | `added=0 removed=1` |
| 5.5 | 换序：内容没丢 | `Counter(base行) == Counter(head行)` |
| 5.5b | 换序：纯搬移的指纹 | `added == removed > 0` |
| 5.6 | `similarity` 合理 | 四组都落在 (0,1] 且互不相同 |
| 5.7 | 不回两份全文 | 输出里 0 个 30 字正文 shingle |
| 5.7b | 每条 hunk 都带 base/head 行号 + ≤120 字样本 | 正则 `^L\d+-\d+$` |
| 5.8 / 5.8b | 每次 compare 留收据 | 4 条；`target` 是「base vs head」、intent 非空 |
| 5.9 / 5.9b | `archive find` 只给位置 | 命中 8 份；每条字段 ⊆ 元数据字段，无正文 |

> 换序组**不用**「期望 added 等于某个具体数字」来判——`difflib` 怎么打破平局
> 是实现细节。改用两条与实现无关的性质：行多重集不变（没丢内容）、
> `added == removed`（纯搬移）。这样断言不会被 difflib 的版本变化带偏。

## 场景 8　长期项目维护

**测什么**：项目跑很久以后，仍然能通过**按需读取**把必要信息捞回来；
而在捞回来之前，一条正文都不许自己进上下文。

**为什么这么测**：这一条的核心不是"能不能读到"，而是**"没主动读就不许读"**。
长期项目里最危险的不是读不到，是一开任务就把 300 行原话吞进来。
所以第 1 条断言是整条场景的地基：先证明它**不会**自动读，再证明它**能**按需读。

**怎么做**：`TEMP/fake-long/` 里放四份互相有可验证关联的资料：

- `OWNER-SPEECH.md`：402 行、**322,553 B**（故意超过 `hard_read_cap_bytes` 262,144 B），
  第 **30** 行是关键原话；
- `CHANGES.md`：301 行，第 12 条**逐字引用**第 30 行那句原话；
- `WORK-HANDOFF.md`：交接纸，指向第 12 条；
- `PROJECT-MEMORY.jsonl`：数据型记忆，11 行。

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| **8.1** | **核心：`index` + `pack` + `archive list` 三步跑完，读取收据仍是 0 条** | `reads.jsonl` 不存在或 0 行 |
| 8.1b | 侧车自报 `read_receipts = 0` | `ctxiso status` 返回 0 |
| 8.2 | 四份资料都列得出来 | 4 个路径都在 |
| 8.2b | 只有元数据 | 5,275 个 30 字 shingle，命中 0 |
| 8.2c | jsonl 的用途摘要是「数据文件，无人读标题」 | 证明数据行不会被当正文 |
| 8.3 | `archive find` 按关键词命中 | ≥ 1 条 |
| 8.4 | 改动图里有指向 OWNER-SPEECH 第 30 行的那一条 | 引用与原话都在 |
| 8.4b | 按 `--scope L30:30` 精确取回 | 取回内容含那句原话 |
| 8.4c | 两边逐字相同 | 改动图里的引用 == 原话流水里的原话 |
| 8.5 | 一次取回有上限 | `truncated=true` 且 `bytes_read <= 262144` |
| 8.5b | 没把整份吞进来 | `bytes_read < file_bytes`（65,538 < 322,553） |
| 8.5c | pack 也没带正文 | `pack.bytes <= 6000` |
| 8.6 | `dropped.json` 给了取回指针 | `how` 里含 `archive list` |
| 8.6b | 按指针能列出位置 | 能列出 `OWNER-SPEECH.md` |
| 8.6c | 压缩后取回与原始一致 | 两次 sha8 相同 + 文本逐字相同 |
| 8.6d | 每次带意图读取都留了收据 | 4 次读取 4 条收据 |

> 8.5 的原话文件必须**大于** `hard_read_cap_bytes`，否则永远不会触发截断，
> 断言就是假的。这条我第一版写成了 74 KB，测了个寂寞。

## 场景 9　新旧系统并存

**测什么**：新开发系统没有破坏原来的中枢，而且这条承诺是**机器证明的**。

**为什么这么测**：这是主人最在意的一条。光在文档里写"我们不动旧系统"没有任何意义，
必须能回答三个问题：旧系统的文件逐字节没变吗？旧系统还能正常干活吗？
新系统有没有偷偷写旧系统？

**判定标准**：

| # | 断言 | 门槛 |
|---|---|---|
| 9.1 – 9.1d | 真仓库 `guard check` | `ok=true`、`changed=[]`、`missing=[]`、`changed_excluding_append_only=[]` |
| 9.1e | guard 本身不空转（假产品） | 34 个受控文件齐；`snapshot` 后 `check` 的 changed/missing 都空 |
| 9.1f | **guard 能抓出真改动** | 改一个字 → `ok=false` 且 `changed` 含 `hub/AGENTS.md`；改回去 → `ok=true` |
| 9.2 | `git status --porcelain` | 只有一行 `?? work/context-isolation/`（只读，无任何 git 写操作） |
| 9.3 / 9.3b | 旧系统仍能干活 | 真实 `hub/tools/state.py` 在假产品上跑 `init→plan→require→work→status` 五步全 0；`status` 输出含 MISSION 与当前阶段 |
| 9.4 | **白名单之外的 UNKNOWN 写句柄为 0** | 见下 |
| 9.4b | 白名单没有过期条目 | 每条都还挂在真实调用点上 |
| 9.4c | 白名单每条都写了原因 | 每条说明 ≥ 20 字 |
| 9.4d | **没有写句柄指向产品目录** | `touches_product` 数为 0 |
| 9.4e | 写句柄只落在侧车 state 目录 | 每处都是 STATE / 白名单 / `pack --out` |
| 9.4f | 唯一的按需写是 `pack --out` | 恰好 1 处，`cli.py` 的 `Path(a.out).write_text` |
| 9.4g | 运行时证明 | 场景 9 是整套最后一个，9.1/9.1b 就是跑完全套之后的复查 |
| **9.4h** | **反向断言：白名单不是摆设** | 见下 |
| 9.5 | 产物装进假宿主家目录 | `03-bundle/dist/hubcore` 复制到 `TEMP/fake-home/hub/` |
| 9.5b | 装出来的东西搜不到源仓痕迹 | 91 个文件里 0 处命中 `D:\`/`context-isolation`/`hub-dock`/`github.com`/`http://`/`user-skills` |
| 9.5c | 每处命中都在明明白白的白名单里 | 白名单项必须写清为什么（如 `tools/hub_ask.py` 的 `hub-lean` 是识别旧测试残留的**检测模式**，不是活路径） |
| 9.5d – 9.5h | **临时改名 `02-hubcore` 跑一遍再改回来** | 改名成功 → 假宿主里三条命令都成功 → 名字改回来且无残留 |
| 9.5i | 新包状态写在包内 `.state/` | 不落在源仓任何地方 |
| **9.5j** | **`check_dist_sync.py` 退出 0** | 护栏：测试必须跑"要发出去的那一份" |
| 9.5k | 产物的 `ctxiso/cli.py` 与源码一致 | **换行归一化后** sha 相同 |
| 9.5l | 产物里没有打包工具 | 不含 `verify.py`/`_bundle_lib.py`/`bundle-meta.json`/`pack.py`/`install.py`/`hosts.py` |
| **9.5m** | 产物里没有运行期残留 | 不含 `.state/` 与 `__pycache__/` |

**9.4 的白名单机制**：自动分类认不出落点的写句柄，必须逐个登记在
`WRITE_WHITELIST` 里（键是「文件::函数」，不是行号），每条写清"实际写到哪里、为什么安全"。
白名单之外多一个写法就红；白名单里少一条（过期）也红。完整 12 条见 `RESULT.md` A 节。

**9.4h 的反向断言**：把 `ctxiso/` 复制到 `TEMP/ctxiso-mutant/`，往副本里注入一个
故意写进 `hub/` 的函数，用同一个扫描器扫这份副本——必须被判成
`kind=UNKNOWN` + `touches_product=True` + 不在白名单里。
**没有这条，白名单就可能只是一张摆设。**

**9.5d 的风险与兜底**：改别人正在用的目录是本套测试里风险最高的一步。
第一次跑的时候回滚失败过一次，`02-hubcore` 被留在改名状态。
现在有四道兜底：`try/finally` + `_swap()` 六次重试 + `atexit` + 下次启动自愈，
并且 9.5h 把回滚结果单列成断言。详见 `RESULT.md` E 节。
