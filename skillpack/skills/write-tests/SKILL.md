# 写测试（Write Tests）

本技能管「要不要写测试、写哪一种」，不管测试目录怎么摆这类口味。核心只有两问：这段代码是否要活过今天；这条测试红掉时，是行为变了还是实现变了。覆盖率是信号不是目标，本技能不产出覆盖率门槛数字。

## 判据（本技能的核心）

- 代码是 spike／一次性原型／只为验证某个可行性 → **不写测试**；判据是产物会被丢弃或重写。代码会被复用、会被改、要活过今天 → 写。
- 手里已有明确的行为规格（输入→期望输出），或是在补一条回归 → test-first 有效，因为期望先于实现存在。
- greenfield／设计敏感（接口与边界还没定）／大任务 → **先设计再测**，不要硬套 test-first。依据：Böckeler 的对照实验里，在 agent loop 内强制 TDD 无增益、甚至略负。
- 落笔前判这条断言测的是**行为**还是**实现**：落在返回值或可观察副作用 → 对；落在私有方法、内部调用次数、日志字符串、SQL 字面量 → 改。
- 反问：这条测试红掉，是因为**行为**变了，还是因为**实现**改了？若是后者，它耦合了实现，重构必改它 → 删掉重写。
- 想把「实现跑一遍的输出」当 expected → 这是 tautological test，永远绿，等于没测。期望值必须来自独立来源（手算、规格、另一条独立路径）。
- 已经烂掉的测试套件比没测试更糟：它把「改坏了」当「正常」，还让人不敢动代码。遇到 → 先删或隔离，再补。
- 覆盖率跌了，但**没有**未覆盖的新逻辑 → 不是问题，不补测试；覆盖率涨了但都是实现细节断言 → 反而是坏信号。
- 新写了分支逻辑且它要活过今天 → 补一条最小测试覆盖那条分支的行为，而不是补一个覆盖率数字。

**三问自查**（每条新测试都要能答，否则不叫完成）：

1. 代码坏了它会失败吗？（删掉实现里一行关键逻辑，它应立刻变红；不红就是在测空气）
2. 它断言的是行为还是实现？
3. 重构之后需要改它吗？（应当**极少**需要）

## When NOT to use（近邻负例）

- 要确认的是「整个需求做完了」而不是「某个函数对」 → 用 `../verify-done/SKILL.md`
- 要写一次性的探索性原型，产物用完即弃 → 用 `../spike/SKILL.md`
- 目标本来就无法自动测试（GUI 像素、硬件时序、人工流程）→ 落回 `../verify-done/SKILL.md` 的手工 check 清单
- 想问的是「这段代码有没有安全问题」 → 用 `../code-audit/SKILL.md`

## When to Pivot

信号与判据见 `../ops/skill-pivot-contract.md`。本技能去向：

| 触发证据 | 换到 |
|---|---|
| 测试红了，但分不清是测试写错还是代码错 | `../fix-bug/SKILL.md` |
| 测试通过，但需求仍可能没做完 | `../verify-done/SKILL.md` |
| 为了让测试通过需要改生产代码结构 | `../implement-feature/SKILL.md`（重构） |
| 测试要驱动真实浏览器/GUI 才有意义 | `../browser-automation/SKILL.md` |

## 定义完成

本技能产出算「完成」的**外部可观测**条件：

- 新增/修改的逻辑有对应测试文件路径与测试函数名
- 新测试在**删掉被测行为后会失败**（三问①有实测证据，不是口头保证）
- 测试运行命令与其 exit code 记录在案（`pytest -q` / `go test ./...` / `npm test`）
- **不产出**覆盖率门槛数字

## 输出契约

```
FACT:       <观察，带来源：命令 / 文件:行 / Evidence ID>
HYPOTHESIS: <可测试断言 + confidence: high|medium|low>（状态见 ../ops/binary-model.md）
QUESTION:   <当前最大不确定点>
NEXT:       <继续 | 换技能 | 停止（附成本判据）>
```

## 置信度词表

词表见 `../ops/confidence-vocabulary.md`。本技能特有判据：

- `confirmed`：故意破坏被测实现后测试变红、恢复后变绿（红/绿各复现一次）
- `low`：测试能跑绿，但从未验证过「删掉实现它会不会红」
