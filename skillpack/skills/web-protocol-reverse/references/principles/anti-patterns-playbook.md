# 反模式手册（Anti-Patterns Playbook）

> **来源**：改编自 `aoyunyang/spider-king-skill`（MIT License）的 `anti-patterns-playbook.md`。原文为英文，本篇为中文改写，**29 条反模式的「诱惑 → 为什么是假进展 → 最小诚实下一步 → 自检」四段结构逐条保留**，未压缩为清单。
> **什么时候用**：当你觉得**某个捷径比下一个证明更快**的时候。原文对此有一句很直白的话：这份文件存在，是因为**软性原则太容易同意、也太容易忽略**。
> - `chrome-devtools` / `js-reverse` MCP 家族 —— **本机未挂载**；
> - `Reqable` / `WireMCP` —— **本机无**，被动流量面用 `(Resolve-ReverseToolSpec -Name 'tshark').Command`（4.6.8，已验证）与 `(Resolve-ReverseToolSpec -Name 'mitmdump').Command` 替代；
> - `iv8` —— **本机无**（社区运行时，PyPI 上不存在）；
> - `DrissionPage` —— 未在本机验证。

## 适用信号

你在心里（或者在 commit message 里）冒出过下面任何一句话，就**先停**，翻到对应条目再改代码：

- 「我先把这个临时浏览器采集器发出去」（→ 第 1 条）
- 「这个 cookie 看着还挺新的」（→ 第 2 条）
- 「helper 现在能加载了，够了」（→ 第 7 条）
- 「我应该直接上更重的运行时」（→ 第 4 条）
- 「第 1 页已经成功过一次了，开始规模化吧」（→ 第 3 条）
- 「profile 管理器打开成功了」（→ 第 27 条）
- 「抓包看起来很完整」（→ 第 28 条）
- 「verifier 返回成功了，收工」（→ 第 23 条）
- 「那个短函数我已经逆出来了」（→ 第 17 条）
- 「HTTP 200 了」（→ 第 14、15 条）
- 「登录成功了」（→ 第 11、12 条）

本篇的判据是**行为形状**而不是具体站点：只要一个动作的**形状**对上了某一条，就按那条处理。原文强调，新条目也必须保持通用性 —— **不要**把活的 cookie、密钥或一次性数值抄进本文件。

## 前置

- 本篇是**行为纠正层**文档，不产出代码、不产出工具调用。
- 四段结构的含义（原文的定义，逐字保留其职责划分）：
  1. **Temptation（诱惑）**：正在发生的那个诱人动作是什么；
  2. **Why it is false progress（为什么它是假进展）**；
  3. **Smallest honest next move（最小的诚实下一步）**；
  4. **Self-check（自检）**：哪一个直接的自检能拦住这次滑坡。
- 相关方法论见 `doctrine-index.md` 第 24 条（反例比口号更能约束行为）。

## 步骤

本篇的「步骤」就是 29 条反模式本身。**用法**：识别出诱惑 → 对号入座 → 读「最小诚实下一步」→ 立刻做那句自检 → 停。

### 反模式 1：把浏览器支撑的重放打扮成「临时采集器」

> Browser-backed replay dressed up as a temporary collector

**诱惑**：

- 调用页面里的 `fetch`
- 用 CDP 或 Playwright 驱动发最后那个请求
- 留一个浏览器 profile 当隐藏依赖

**为什么它是假进展**：

- 未解决的协议状态**依然没被解释**
- 重放证明依赖一个**页面世界**，而不是本地产物
- 交接变得无法推理、无法维护

**最小的诚实下一步**：

- 识别浏览器**到底额外加上了哪个决定性产物**
- 在**最近的那个稳定边界**上把那个产物收割出来
- 把它**交回 Python**，由 Python 发出真实 HTTP 重放

**自检**：

> 如果浏览器进程消失了，采集器还工作吗？

### 反模式 2：因为「这一次能用」就写死当前的轮换 cookie / token / header

**诱惑**：

- 把当前的 cookie header 粘进配置
- 冻结某一个**碰巧**还能过的 token 或旁挂载荷
- 把一个当前样本当成一种刷新策略

**为什么它是假进展**：

- 它只证明了**一个快照**，没证明写入者或刷新路径
- 过期时间、槽位位置、会话绑定**全部仍然未知**
- 之后的失败会被误诊成签名器 bug

**最小的诚实下一步**：

- 证明**谁在写**这个产物
- 证明它**在线上（wire）哪里被消费**
- 只重建 / 刷新重放**实际需要**的那个权威产物

**自检**：

> 采集器能在**不手动重抓**的情况下再次拿到这个产物吗？

### 反模式 3：一次走运的成功之后就规模化

**诱惑**：

- 一页跑通就开始做分页
- 在还没有一条稳定重放路径之前就加并发
- 在一条新鲜会话链被证明两次之前就瘦身运行时

**为什么它是假进展**：

- 一次走运的通过**可能掩盖**了陈旧状态、会话链耦合、或页面专属容忍度
- 之后的失败会和规模化效应**混在一起**

**最小的诚实下一步**：

- 同一条最小请求**至少重放两次**
- 用**同一套 collector 路径**证明第 2 页或一个 next cursor
- **只有到这一步**才扩大范围

**自检**：

> 同一个单页请求在一次全新的重复上还成功吗？

### 反模式 4：因为当前那一级让人沮丧，就一次跳好几级

**诱惑**：

- Python 不一致 → 广泛的内嵌运行时
- 本地运行时能加载 → 大范围的宿主 patch
- 一条路由被拦 → 全路由范围的传输层「cargo cult（照搬）」

**为什么它是假进展**：

- **真正的盲点始终没被命名**
- 对照基线被毁掉
- 更重的层会**掩盖**更简单的未解决错误，比如槽位位置或序列化

**最小的诚实下一步**：

- 写阶梯日志（ladder log）
- 证明当前这一级的**确切失败点**
- **只**升一级

**自检**：

> 你能说出更重的那一层**要回答的到底是什么盲点**吗？

阶梯模型见 `../triage/escalation-ladder-playbook.md`。

### 反模式 5：在拿到干净基线之前就装大范围 hook

**诱惑**：

- 因为目标看着难，立刻注入全局 hook
- 在抓到一条干净请求之前就下大范围断点
- 把 hook 导致的失败当成「这个站只能浏览器跑」的证据

**为什么它是假进展**：

- **观察者效应**会改变时序、身份、或 verifier 行为
- 干净契约在**被冻结之前**就已经丢了

**最小的诚实下一步**：

- 抓一组**完全没被插桩**的基线请求 + 响应
- 把 hook **向外移动**到最窄的稳定边界
- 显式比较「有 hook」与「干净」两种行为

**自检**：

> 失败形态**是在**你的插桩落地**之后**才变化的吗？

---

### 反模式 6：去逆那个「看得见的 helper / 看得见的参数」，而不是线上的变异点

**诱惑**：

- 因为页面上有个叫 `sign` 的东西就追它
- 对着「可见的端点」写代码，而不是对着**真实路由**
- 在 wrapper 重写之前就相信业务载荷

**为什么它是假进展**：

- 真正的契约可能住在 **wrapper、interceptor 或出口（egress）变异**里
- **正确的 blob 放在错误的槽位**，照样失败

**最小的诚实下一步**：

- 追踪那个**规范化的变异点（canonical mutation point）**
- 抓到**最终的、线上形状的**请求
- 重建真正跨过边界的那部分

**自检**：

> 你正在逆的那个东西，和线上**实际发出去的**东西完全一致吗？

---

### 反模式 7：把「helper 加载成功 / 异常变少 / 输出形状像浏览器」当成协议成功

**诱惑**：

- token 长度「看起来更接近了」
- 运行时抛的异常变少了
- cookie 形状看起来更像真的

**为什么它是假进展**：

- 这些**只是本地健康信号**
- 它们**不能证明**真实请求能重放

**最小的诚实下一步**：

- 发出**真实的业务请求**
- 校验**响应语义**，不只是状态码或形状
- **重复**这次重放

**自检**：

> 真实目标请求现在能**反复**成功吗？

---

### 反模式 8：用易变的抓包覆盖稳定脚手架

**诱惑**：

- 用新的目标 blob 替换用户维护的 fixture
- 直接编辑稳定 helper，把本次运行的产物写进去
- 让**可复用代码**和**易变抓包状态**变得模糊

**为什么它是假进展**：

- 之后的 diff **变得不可读**
- 稳定路径被**某一次运行**污染
- 升级分析**失去干净基线**

**最小的诚实下一步**：

- 新抓的样本放进**任务本地缓存**
- 从易变产物**生成临时 runner**
- 只有当这个经验被证明**可复用**之后，才更新稳定脚手架

**自检**：

> 明天你还能从一个干净的稳定基线重跑这次 diff 吗？

### 反模式 9：相信页面文案所说「某个 cookie 或 session id 参与签名」

**诱惑**：

- 因为页面「警告」说它重要，就把 `sessionid` 写死进 token 的 preimage（原像）
- 在登录没解决之前，拒绝原型化一个匿名列表采集器
- 把「提交需要账号」的要求混进**每一个**列表或详情请求

**为什么它是假进展**：

- **页面文案不是线上证据**
- 列表链、详情链、提交链**通常有不同的会话契约**
- 一个错误的 preimage 会把大量逆向时间浪费在一个**根本不存在的密码学问题**上

**最小的诚实下一步**：

- 分别抓「**带**该 cookie」和「**不带**该 cookie」两种真实请求
- 从线上给字段分类：静态 / 服务端时间 / 签名器输出 / 账号状态
- 当业务响应在**不登录**时已经成功，就**保持匿名采集可用**
- 只对**真正 401 或答案会变**的那条链要求会话

**自检**：

> 去掉这个 cookie，改变的是**业务响应**，还是只是**后面的提交路径**？

### 反模式 10：因为算法名字对上了，就把标准摘要库当成「已完成」

**诱惑**：

- 在源码或 UI 文案里看到名字之后，直接换成原版 MD5 / SHA / SM3
- 长度看起来对了，就跳过中间字（word）检查
- 只移植 happy-path 的常量，忽略由环境选择的分支

**为什么它是假进展**：

- **IV、轮常量、打包掩码、压缩掩码**是常见的重写点
- **一个错误的 `ROTL` 边界用例**能让某些页面过、某些页面不过
- 浏览器分支的常量可能与 Node 或 fallback 分支不同

**最小的诚实下一步**：

- 冻结**一组**抓下来的 preimage 与 digest
- 把 IV、常量、打包、压缩步骤**逐项 diff** 标准算法
- **先在本地复现浏览器分支**，再做 Python 移植
- 加一个**定输入自检**，让「偷偷换成标准库」这件事**大声失败**

**自检**：

> 你本地的标准库和那个固定样本**完全一致**，还是只有位长一致？

### 反模式 11：把账号登录 cookie 当成已经完成的业务会话

**诱惑**：

- 密码或 token 登录返回成功后就停
- 在 tenant / role / 数据范围激活之前就导出 cookie
- 把一个「只有登录态」的 jar 交给采集器，好像每个页面都已经解锁

**为什么它是假进展**：

- 很多后台在**认证之后仍然保留可变的业务上下文**
- 于是采集器带着「登录成功」的绿灯，**去抓了错误的店铺 / 供应商 / 组织**

**最小的诚实下一步**：

- 把 **Gate A 登录** 和 **Gate B 业务身份激活**拆成两件事
- 导出之前**重读最终身份**
- 多层场景转 `../state/multi-context-session-playbook.md`

**自检**：

> 导出出来的会话的**激活上下文**与任务配置一致吗（而不只是账号 id 一致）？

### 反模式 12：信任「切换接口」的返回值，跳过最终身份重读

**诱惑**：

- 看到 update-session 或 switch-context 调用返回 HTTP 200 或 `success=true` 就接受
- 因为「值字段看起来够了」就省掉一个必填的 type 字段
- 不打开权威身份面，直接进入采集

**为什么它是假进展**：

- **部分激活**可能留下一份**旧的或空的数据范围**
- 这个失败是**静默**的，事后看起来像「数据 bug」或「过滤器 bug」

**最小的诚实下一步**：

- 与成功路径的 UI 载荷**逐字段比对**
- 从**最终页面或 introspection 端点**重读身份
- 任何一层缺失或不匹配，就 **fail closed（失败即停）**

**自检**：

> 如果把数据范围的 type 或 value 去掉，你的验收**还**能过吗？能的话，这个门禁太弱了。

### 反模式 13：把 UI 标签当协议 id 提交，或者取第一个模糊匹配

**诱惑**：

- 因为操作员选的就是这个，就 POST 那个可见的中文名或本地化名
- 复用**另一个账号**的资源 id
- 枚举返回多行时，直接取 index 0

**为什么它是假进展**：

- 激活需要的是**活的授权码或授权值**
- 模糊匹配会造出**上下文错误的会话**，而它们看上去仍然是已认证的

**最小的诚实下一步**：

- 通过**当前账号的授权响应**来解析标签
- 要求**恰好一个**匹配
- **零匹配或多匹配都要停**

**自检**：

> 一个被改名的标签，或一个重复标签，会让你的解析器**大声失败**吗？

---

### 反模式 14：把 HTTP 200 当成异步导出任务的「创建成功」

**诱惑**：

- 创建端点返回 200 或一个含糊的成功标志之后就停
- 因为「请求看起来对」就跳过历史 diff
- 轮询**第一个出现的**成功任务

**为什么它是假进展**：

- **空成功**、方法用错、body 位置放错，**经常照样返回 200**
- 于是采集器下载了**别人的、更老的**文件

**最小的诚实下一步**：

- 在创建**之前**给任务 id 拍快照
- 要求一个**新的任务 id**，并且条件匹配
- 转 `../state/async-export-job-playbook.md`

**自检**：

> 你能说出**一个在这次运行之前并不存在**的任务 id 吗？

---

### 反模式 15：复用「历史最新」的那个导出任务

**诱惑**：

- 直接抓历史列表的第 0 行
- 复用「创建之前就成功过」的任务来「省时间」
- 忽略过滤条件或字段集的不匹配

**为什么它是假进展**：

- 你证明的是**下载**，不是**创建**
- **错误的日期范围或更少的列**被当成新鲜数据持久化了

**最小的诚实下一步**：

- 用**创建返回的 id**，或**创建之后**的新 id 来隔离
- 匹配业务过滤条件与请求字段
- **只能看到旧任务时就失败**

**自检**：

> 这个任务 id 在**创建前的快照**里是缺席的吗？

---

### 反模式 16：把「重新生成旧任务」的流量当成「首次创建」的契约

**诱惑**：

- 从「重新生成旧任务」复制 method 和 body
- 因为旁边那条路由能用，就对**错误的序列化**签名
- 没有专门抓包就宣布「首次创建已解决」

**为什么它是假进展**：

- 「重新生成」可能需要一个**旧任务 id**，而且过滤条件**放置的位置不同**
- 签名器可能**在一条路由上过、在另一条上过不去**

**最小的诚实下一步**：

- 抓**一条干净的首次创建**请求
- 比对 method、query、body、content-type 和签名覆盖范围
- 把**未证明的边界显式标出来**

**自检**：

> 你的创建证明来自**首次创建的线上证据**，还是只来自「重新生成」？

---

### 反模式 17：把唯一反编译出来的那个短 signer 当成唯一的写入者

**诱惑**：

- 一段短的 hash 或 compress 路径被认为已经完全离线恢复
- 字段名与线上 verifier 参数对上了
- 自检向量看起来完美

**为什么它是假进展**：

- **线上成功的那个值，可能是一段更长的、由挑战脚本写出的 body，来自**不同的写入者**
- 哪怕短生成器对它自己的路径是正确的，线上**仍然返回挑战 HTML**
- 把短生成器打包，**等于把一条科研路径冻结成了产品交付**

**最小的诚实下一步**：

- 把**短的科研输出**与线上成功值的**长度和前缀**做比对
- 把那个字段名对应的**每一个写入者栈**都画出来
- **只交付线上被接受的那一类**

**自检**：

> 线上成功的请求，真的携带了你那个**短 token 的形状**吗？

---

### 反模式 18：把「样本精确重放」叫作「协议自动化」

**诱惑**：

- 存了一堆带长 token 的绝对 URL，**逐字**请求还是能返回业务 JSON
- `jobs.csv` 在「样本模式」下就能填满

**为什么它是假进展**：

- 精确重放**不能证明**新时间戳 / 新页面 / 新会话能被重新生成
- **轮换的挑战状态依然没有解决**
- 交付门禁要求的是**反复的线上成功**，不是**存档回放**

**最小的诚实下一步**：

- 通过**真正的写入者**或挑战执行器，在**新时间戳或新页面上**重新生成
- **样本模式只保留为诊断用途**

**自检**：

> 你能在**不复制旧最终 token** 的情况下，铸出一个新的 URL 绑定产物吗？

---

### 反模式 19：重定向里已经带上了产物，还在继续逆 encrypt

**诱惑**：

- 挑战 helper 或运行时**已经导航到一个带决定性参数的 URL**
- 本地执行器还在抛导航或 DOM 噪声
- encrypt 模块看起来还没逆完

**为什么它是假进展**：

- **最近的那个稳定产物已经足够**让 Python 重放了
- 产物之后的异常**往往是噪声**
- 完整逆 encrypt 以后可能仍然有用，但**它不是第一道交付门禁**

**最小的诚实下一步**：

- 收割 `redirectUrl` 或 cookie 字符串
- 从 Python 重放
- **只有当不依赖它的重新生成仍然失败时**，才回去继续逆 encrypt

**自检**：

> helper 输出里**已经有**一个能被 Python 重放的产物了吗？

---

### 反模式 20：把「应用签名器」和「WAF / 挑战 verifier」合并成一个问题

**诱惑**：

- 浏览器请求里**同时**出现 HMAC/sign 请求头和挑战参数
- 一张逆向工单试图**一次性解决所有字段**

**为什么它是假进展**：

- **这些门禁可以互相独立**
- 挑战重试路径**可能根本不需要**应用签名器
- 应用签名器恢复成功的同时，verifier 恢复仍可能被卡住（反过来也一样）

**最小的诚实下一步**：

- 用**消融实验（ablation）**证明每一个门禁的必要性
- 交付**能让线上业务响应通过的最小字段集合**

**自检**：

> 按线上消融的结果，哪些字段是**必填**、哪些是**可选**、哪些是**只能浏览器**？

---

### 反模式 21：把「自动化浏览器里手动划动失败」当成轨迹真相

**诱惑**：

- 一个人在 DrissionPage / CDP 驱动的 Chrome / 挂了 hook 的 profile 里划动，**仍然失败**
- 团队于是断定「轨迹算法是错的」，开始搜轨迹方案

**为什么它是假进展**：

- 自动化标记、调试端口、注入的 hook、新 profile，**即使配真实人手部运动**也可能过不了风控门
- **被污染的负样本**会教错失败面
- **干净的普通浏览器成功样本，可能早就证明了这一族轨迹是可接受的**

**最小的诚实下一步**：

- 尽可能在**自动化所有权之外**抓**一条干净的正样本**
- 在**同样的会话假设**下比较：干净成功 / 污染失败 / 协议重放
- 读 `../triage/positive-sample-hygiene-playbook.md`

**自检**：

> 在责怪轨迹生成之前，你有**至少一条来自非自动化浏览器路径的成功样本**吗？

---

### 反模式 22：结构已经被接受了，还在继续调轨迹

**诱惑**：

- token 结构、校验和、旁挂载荷的 HTTP 状态都正常了，**最终 verify 仍返回一个「像风控」的拒绝**
- 于是下一步就加更多合成轨迹、距离尺度和 sleep 抖动

**为什么它是假进展**：

- 风控拒绝可能来自**共享状态不一致、遥测语义缺失、不可能的墙钟时序、或者环境评分**
- **轨迹搜索只会放大噪声**，无法定位失败面
- **连续失败本身还会加重环境风险**

**最小的诚实下一步**：

- 用**受控消融**定位错误家族
- 复查「完整基线 / 稀疏增量」的一致性与**真实时间线**
- **只有到这一步**才去改行为载荷或答案载荷
- 如果环境风险被牵连，**先**换出口 / IP 或修样本卫生，**再**考虑更多轨迹变体
- 读 `../triage/verifier-error-localization-playbook.md`

**自检**：

> **哪一个单独受控的省略**会改变拒绝的家族？它和轨迹有关吗？

---

### 反模式 23：把「verifier 语义成功」叫作「完成的采集器」

**诱惑**：

- verifier 端点返回了平台侧的 accepted code 或 flag
- 在**第一个消费这份授权的业务请求**之前就停止交付

**为什么它是假进展**：

- **verifier 成功可能是中间态**
- token 放置位置、query 名、cookie 槽位、成功参数别名、body 封装方式，**仍然决定业务侧是否接受**
- **一个不能重新拉取原始文档或 API 的采集器，不算交付**

**最小的诚实下一步**：

- 在**同一轮内**证明第一个下游消费者
- 用**内容指纹**定义业务通过判据，不只是 HTTP 状态码
- 让 verifier 与消费者的封装**留在同一条会话链上**

**自检**：

> 在 verifier 接受之后，**原始的业务 URL** 能通过重新生成的授权返回**非挑战内容**吗？

---

### 反模式 24：把「只存在于磁盘上」的 MCP 家族当成已挂载

**诱惑**：

- checkout 目录或下载目录里**有** `chrome-devtools`、`js-reverse`、`reqable` 等 MCP 源码
- 于是就按「这些服务器已挂载」来路由

**为什么它是假进展**：

- **可用性由当前 agent 会话的工具注册表 / schema 决定，不是目录列表**
- 随后编造的 initiator 或变异结论**看上去完整，而实际上没有任何工具真的跑过**

**最小的诚实下一步**：

- **先检查实际挂载的工具**
- 记录 `missing_mcp`，然后退回到可用的证据面，或者**降一档交付形态**

**自检**：

> 在第一次对目标动手之前，你选的那个 MCP 家族**出现在**实时的工具 schema 里了吗？

---

### 反模式 25：在纯产物任务上强推「双浏览器首轮」

**诱惑**：

- 用户给的是 HAR、请求文本，或者一份被动抓包
- 为了满足 `live-target` 的仪式，**两个浏览器家族都被打开**

**为什么它是假进展**：

- **产物型任务绝不能凭空发明浏览器证据**
- 双首轮只适用于**新鲜的 Web live 目标**；APK / app / 小程序为主的工作**不在本技能范围内**

**最小的诚实下一步**：

- 停留在 `evidence-reuse` 或离线路线，**直到确实需要线上接受度**为止
- 在没有授权做浏览器首轮时，把 **live acceptance 标为未证明**

**自检**：

> 如果**根本不存在浏览器 MCP**，你的下一个答案还成立吗？

---

### 反模式 26：让 `chrome-devtools` 和 `js-reverse` 同时对目标动手

**诱惑**：

- 为了省轮次，**同时**在两个家族里打开页面

**为什么它是假进展**：

- **profile 与所有权冲突会毁掉干净基线**
- initiator 证据与线上证据**变得不可比**

**最小的诚实下一步**：

- 只保留**一个** `TARGET_ACTIVE` 家族
- **完成顺序交接**之后再切换

**自检**：

> 在这一批工具调用里，**只有一个**浏览器家族在对目标动手吗？

---

### 反模式 27：把「环境 provider 启动成功」当成协议成功

**诱惑**：

- AdsPower 或别的 profile 管理器干净地打开了
- 于是**在没有基线、没有变异证明**的情况下宣布交付或已理解线上行为

**为什么它是假进展**：

- **ENV provider 只提供一个「面」（surface）**
- 附着（attach）、基线、变异、重放**全部未被证明**

**最小的诚实下一步**：

- 拿到一个**可调试的端点**
- 在 **attach 所有权**下，先跑 chrome 的证据，再跑 `js-reverse` 的证据

**自检**：

> 在 profile 启动**之后**，有抓到一条业务请求并完成关联吗？

---

### 反模式 28：把被动抓包 / PCAP 当成签名器恢复

**诱惑**：

- `reqable` 或 WireMCP 显示了流量，于是**跳过签名重建**
- 因为抓包「看起来很完整」，于是宣布采集器已完成

**为什么它是假进展**：

- **store（存储）证明的是出口历史，不是本地再生成能力**
- **PCAP 可见性本身既不是传输 profile 的证明，也不是算法的证明**

**最小的诚实下一步**：

- 从抓包里**抽取变动字段**
- 在进入无浏览器重放之前，先用**固定向量**做离线重建

**自检**：

> 你能在**不把抓到的一次性值当硬编码密钥**的前提下，重新生成那个请求吗？

---

### 反模式 29：把 MCP 浏览器运行时留在采集器里

**诱惑**：

- Playwright、CDP 页面驱动，或者 MCP 浏览器调用，作为「临时兜底」留在最终运行路径里

**为什么它是假进展**：

- **浏览器支撑的重放不是协议采集器**
- 交付门禁**禁止**把浏览器自动化作为最终路径

**最小的诚实下一步**：

- 在纯 HTTP 重放跑通之前，把它们**降级为 `evidence` 或 `local-proof`**
- 从 `main.py` / `collector/main.py` 里**移除 MCP 运行时导入**

**自检**：

> **把浏览器 MCP 服务器全部停掉**之后，你的右键入口还能成功吗？

### 新增反模式的条目格式

当一个捷径在**一个以上**任务里复发时，按下面这个形状加进来：

```markdown
## 反模式 N：<简短名称>

**诱惑**：
- ...

**为什么它是假进展**：
- ...

**最小的诚实下一步**：
- ...

**自检**：
- ...
```

**保持通用。不要**把活的 cookie、密钥或一次性数值抄进本文件。

### 最终规则

> 如果一个捷径**经不起一次直接的自检**，它就不是捷径。
> 它是伪装成进展的债（debt disguised as progress）。

## 判据

「做到哪一步算完成」——本篇是判定层文档，判据分两类。

### 一、本篇「使用完成」的判据（可外部观测）

- 你能对你刚才那个动作，**指名一条具体的反模式编号**；
- 你**执行了**那条的「最小诚实下一步」，而不是只读了一遍；
- 那条的**自检问题被你真的回答了**（不是默读过去）；
- 如果这条自检的答案是「否」，那么**任务还没完成** —— 无论代码看起来多能跑；
- 你能说出：如果去掉浏览器 / 去掉抓包 / 去掉那个短 signer，**还剩下什么是可复现的证据**。

### 二、每条反模式被「解除」的判据（对照自检的外部观测）

| 反模式 | 解除判据（外部可观测） |
|---|---|

## 常见坑

按「最容易在读本篇时再次踩」排序：

1. **把反模式清单当成「已经检查过的证明」**。读到「不要写死 cookie」不等于你已经证明了它的写入者。第 2 条的解除判据是**可重新生成**，不是「你记得别写死」。
2. **自检问题被默读跳过**。本篇的每条自检都是问句，**必须回答**。绝大多数滑坡都是在心里默默跳过自检时发生的。
3. **第 24 条与第 25 条在本机是最容易触发的两条** —— 本机没有 `chrome-devtools` / `js-reverse` / `Reqable`（见文末对照表）。这两个「未挂载」是**能力缺口**，**不是**「这个目标只能浏览器跑」的证据。两者的区别见 `doctrine-index.md` 第 17 条（传输准入）与第 10 条（观察者效应）。
4. **第 14 / 15 条被当成一条**。原文分成两条是因为它们对应两种**不同的错误**：14 是「没验证创建」，15 是「验证了下载」。混成一条会让你在「下载成功」时误以为创建也通了。
5. **第 17 条被读成「短 signer 无用」**。原文说的是**交付形态**问题：短 signer 对它自己的路径可能完全正确，但**线上写的是另一个**。不要因为第 17 条就丢弃一个正确的科研实现。
6. **第 21 / 22 条顺序颠倒**。先有干净正样本（21），才有资格谈轨迹调整（22）。反过来做，就是原文说的「唯一的负样本全来自污染环境时，拿下一个小时去变异轨迹」。
7. **第 5 条被当成「不要用 hook」**。原文不是禁止 hook，是要求**先有干净基线**，然后把 hook **向外**移到最窄边界。
8. **第 20 条被简化成「分两次做」**。原文要求的是**消融证明**，不是「拆成两个工单」—— 没有消融，你不知道哪些字段真的必要。
9. **第 4 条的「只升一级」被当成「必须按固定顺序」**。阶梯是**成本排序**，不是**流程门禁**。如果你能一句话说清盲点并证明更重的层是最小解，跳级是合法的 —— 但要**写下那句话**。
10. **新增条目时把具体数值抄进来**。原文明确禁止。新条目写的是**行为形状**，不是某个站的现场。
