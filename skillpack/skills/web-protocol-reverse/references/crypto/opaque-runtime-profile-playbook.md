> **来源声明**：本文改编自外部仓库 `aoyunyang/spider-king-skill`（MIT License）的 `opaque-runtime-profile-playbook.md`。原文为英文，此处译为中文并按本包六段式规范重排；技术术语保留英文原词并附中文，AI 检索时中英文均可命中。源文档技术内容经核对**未发现错误**，未作技术性修改。**本机化重点**：源文档引用的 `scripts/transform_trace_diff.py` **在本包中不存在**（见文末勘误），已替换为本机实测可跑的等价校验写法。

> **什么时候用**：一个不透明的 signer（签名器）、指纹载荷、telemetry sidecar、验证器证明（verifier proof）、或 packed 请求，**通过多个运行时阶段组装**，而**本地移植需要捕获的环境或状态输入**才能对齐。
>
> **平台与本机状态**：Windows 10 x64。`python 3.12`（`D:\EXE\python\python.exe`）、`node v24.20.0`（`D:\Tools\Node\node.exe`）、`playwright（模块在 `D:\EXE\python\Lib\site-packages\playwright`）` **本机可用**。`iv8` **本机无**。

> 或 `launch(executable_path=<显式路径>)`。照抄裸 `launch()` 一定失败。

## 适用信号（Recognition signals）

### 在这里路由（Route here when）

- **公开的 VM 或 helper 边界已知**，但**没有暴露出第一个分叉的变换**
- 存在一个**稳定的 mode / transform / serializer / packer 派发器**
- **完整的捕获运行可以回放**，但**来自不同运行的片段会失败**
- **Python 移植只有在冻结一整份运行时 profile 时**才对得上
- 一个**已接受产物的池子**有被误当成「新鲜本地生成」的风险

### 不要在这里路由（Do not route here merely because）

**仅仅因为 bundle 被混淆了。**

**先证明公开的输入、输出、状态写入、或请求出网。**
**只有在外层边界被证明不够之后**，才做 mode 级追踪。

## 前置（Entry conditions）

1. **一次完整的成功运行** —— 这是**一个原子证据单元**（源文档核心规则第 1 条）
2. **主动资产的哈希**（脚本 / 字节码 / WASM / bundle），以及 helper 与运行时版本
3. **一个 stage trace 的落盘格式**（见下面步骤 3）
4. ⚠ **源文档提到的 `scripts/transform_trace_diff.py` 在本包中不存在** —— 见「源文档勘误」第 1 条。替代方案见步骤 3 末尾。

## 步骤（Working method）

### 核心规则（Core rules）

1. **一次完整的成功运行 = 一个原子证据单元。**
2. **只插桩最窄的稳定阶段边界，而不是每一条 opcode。**
3. **在证据给出名字之前，把未知字节保持为不透明值。**
4. **固定输入的字节对齐是本地证明；活体业务接受才是最终证明。**
5. **如实报告交付是 algorithmic（算法化）、snapshot-driven（快照驱动）、还是 pool-backed（池回放）。**

### 三类交付必须分开（Truthful delivery classes）

#### 1. 算法化生成（Algorithmic generation）

采集器**重建了每一个决定性变换**，能**仅凭显式的当前输入**产出新鲜的、已被接受的产物，**不依赖任何捕获的产物或运行时 profile**。

> 这一类描述的是**签发独立性**，**不是实现语言**。
> 另需单独报告：实现是**纯 Python**、用了**极小的本地 JS / WASM helper**、还是**仍然依赖另一个运行时**。

#### 2. 快照驱动生成（Snapshot-driven generation）

采集器在本地跑通了恢复出来的变换，**但仍从一整份捕获的运行时 profile 里选择输入**，该 profile 含环境、不透明、或版本特定的输入。

> 正常执行期间它**可以是** browser-free 且 runtime-free，
> 但它**依赖捕获**。**必须证明** profile 的新鲜度、范围、以及升级行为。
> **当 profile 的写入者仍然未知时，不要把它描述为「完全生成式」。**

#### 3. 池回放（Pool-backed replay）

采集器从**池子里挑一个此前已被接受的最终产物或 token**。
**本地不一定跑任何变换。**

> 把它当作**诊断对照**，或**一个被明确接受的有界回退**，
> **而不是「生成能力被恢复」的证明**。
> 大池子**不解决**签发、过期、会话绑定、一次性行为、或刷新。

### 证据权威顺序（Evidence authority）

**冲突时按此顺序裁决：**

1. **最终的 wire 产物**，以及下游业务接受
2. **来自主动资产的干净运行时阶段追踪**
3. **固定输入的本地阶段追踪**
4. **解码后的最终载荷**，以及实测的分段偏移
5. **当前实际下发的源码与运行时配置**
6. **推断出来的字段名、注释、或「我记得的布局」**

> 长度、前缀、看起来合理的编码 —— 这些是**分诊信号**，**不是字节对齐，也不是目标接受**。

### 恢复工作流（Recovery workflow，10 步）

#### 1. 冻结一条干净基线

**在加广泛插桩之前**，先记录一次成功的运行：

- 主动脚本 / 字节码 / WASM / bundle 的哈希
- helper 与运行时版本
- 消费该产物的路由族与请求槽位
- 显式的配置与会话范围
- 时间戳、随机数、nonce、以及环境输入策略
- 最终产物字节，或一份本地含密样本
- 下游响应族，以及业务接受锚点

> **含密的原始追踪只在任务内保存（task-local）。**
> **报告里只放哈希与脱敏结构。**

#### 2. 证明外层边界

**映射：**

- 公开的 VM 或 helper 输入
- wrapper 的返回值
- 权威的状态写入
- 请求出网的改写
- 最终消费者与**确切的字段槽位**

> **如果这个边界已经足以复现产物，就停在这里。**
> **不要**因为解释器「看起来很有意思」就打开它。

#### 3. 捕获稳定的阶段检查点

当外层边界不够时，**优先选择每个决定性阶段都必经的** dispatcher、transform table、serializer 入口、或 packer 调用。

**每次调用捕获：**

- 序列索引，以及稳定的阶段名或 mode 标识
- 同一阶段重复出现时的**出现序号**
- **精确的输入与输出字节**
- 输入与输出长度
- 用于序列化该追踪的编码
- 可能改变输出的**显式旁路输入**
- **干净运行 vs 插桩运行**的产物哈希

> **在阶段级证据证明「决定性变换无法隔离」之前，不要铺开做 opcode 级日志。**
> 用一次干净运行与一次插桩运行对比，以**检测观察者效应（observer effect）**。

**本机 trace schema**（源文档给的最小形态，结构保留）：

```json
{
  "trace_version": 1,
  "source": {
    "artifact_sha256": "redacted-or-hash",
    "runtime": "name-and-version"
  },
  "stages": [
    {
      "name": "normalize",
      "input": {"encoding": "base64", "data": "..."},
      "output": {"encoding": "base64", "data": "..."}
    },
    {
      "name": "pack",
      "input": {"length": 128, "sha256": "..."},
      "output": {"length": 96, "sha256": "..."}
    }
  ]
}
```

> **原始描述符**（`encoding` + `data`）能报告**第一个字节不匹配的位置**。
> **脱敏描述符**（只有 `length` 与 `sha256`）**在比较的同时不把含密字节复制进报告**。

**⚠ 本机替代 diff 工具**：源文档要求每次改动后运行
`scripts/transform_trace_diff.py`，但**该脚本在本包中不存在**（见勘误）。
本机实测可用的等价做法：

```powershell
# 两份 trace 先各自规范化，再按阶段名逐个比对。
# 只看第一个分叉的阶段 —— 这正是 transform_trace_diff 的用途。
D:\EXE\python\python.exe compare_traces.py a.json b.json
```

比对逻辑（本机可直接实现，无需外部包）：
1. 按 `stages[].name` 建索引
2. 对每个同名阶段，**先比 `length`**，长度不同即报告
3. 长度相同则比 `sha256`
4. 有原始 `data` 的，直接找**第一个字节不同的下标**并报告
5. 输出**第一个分叉的阶段名**，且**到此为止**

#### 4. 建立分段图（Segment map）

**只解码到证据支持的程度。**
分段边界从**观察到的阶段输出长度**、固定前缀、分隔符、长度字段、以及 wrapper 框架推导。

**每一段记录：**

- 偏移与长度
- 产生它的阶段与出现序号
- 该段是**变换输出**、**复制输入**、**wrapper 元数据**、还是**无法解释的间隙**
- 编码与字节序（endianness）
- **在重复的干净捕获之间是否稳定**

> **把无法解释的间隙保持为不透明。**
> **不要**仅仅因为一个样本「看起来像时间戳、平台值、或校验和」就给这些字节改名。

#### 5. 建立一份原子运行时画像（Atomic runtime profile）

**一份运行时 profile 应保持一次内部自洽的运行：**

- profile id 与捕获哈希
- 主动资产与运行时版本
- 显式的环境与配置输入
- **每个输入的来源与语义置信等级**
- 带偏移与哈希的不透明块
- 本地生成所需的阶段输入
- **用于确定性证明的期望最终产物哈希**
- 已知时的会话、路由、账号、以及新鲜度范围

**用这样的置信标签**：`observed-name`（观察到的名字）、`behavior-proven`（行为已证明）、`opaque`（不透明）。

> **从源码抄来的名字不是行为证明。**

**把易失捕获放在任务内的证据区，与稳定的 helper 代码分开。**
**不要**把一大包轮换的产物池藏在压缩源码里，然后叫它「算法」。

#### 6. 一次只移植一个变换

**重实现最小的那个阶段，比对它的固定输入与输出，然后再进入下一个阶段。**

**常见的跨运行时危险：**

- 自定义 Base64 字母表、填充、或字节到文本转换
- **UTF-8 与 UTF-16 码元行为差异**
- 有符号移位、整数溢出、以及字节序
- **JavaScript 的双精度与舍入**
- varint、TLV、紧凑 JSON、以及长度前缀规则
- **对象键顺序与归一化**
- 「源码数组」与「返回的已变换字节」之间的差别

> **每一次改动之后，修复第一个分叉的阶段，而不是在更靠后的分段里做补偿。**

#### 7. 证明整份 profile 的一致性

**不要**把 header、环境块、随机块、间隙、或尾部从**邻近的成功运行**里拼接过来，除非有受控测试证明那些部分是独立的。

**用负向对照（negative controls）：**

- **改一个已知输入**，确认预期的阶段确实变了
- **拼接一个疑似独立的分段**，观察接受或字节对齐是否被破坏
- **篡改一个不透明块**，确认校验器**能够**检测到拒绝

> **如果只有完整的捕获才能工作，就把完整 profile 当作原子单元选择。**
> **保持相关字段在一起。**

#### 8. 把证明用的随机性，与活体生成分开

**确定性证明模式（deterministic proof mode）** 冻结 profile、时间戳、nonce、随机字节，以及其他变动输入。
**它必须复现每一个阶段，以及最终产物。**

**活体生成模式（live-generation mode）** **只刷新那些其写入者与可变性都已被证明的字段**。

> **不要独立地随机化不透明字节，或相关的 profile 分段。**
> 整份 profile 选择比分段混合更安全，
> 但**只要 profile 本身无法被重新生成，它仍然是快照驱动的。**

#### 9. 验证新鲜度与范围

**在完整字节对齐之后**，跑**能回答真实不确定性的最小接受矩阵：**

- 原始会话上的**新鲜产物**
- **同一会话上的第二次使用**
- **另一个干净会话上的同一产物**
- **由同一 profile 新生成的产物**
- **同一路由上的另一份完整 profile**
- **消费该产物的第一个下游业务请求**

> **每次只改一个变量。**
> **在一条新鲜的单请求路径能重复成功之前，不要加并发。**

#### 10. 分层归类失败

**保持这些层分开：**

1. 捕获或追踪损坏
2. 变换或跨运行时对齐失败
3. 最终组装、编码、框架、或槽位放置失败
4. 新鲜度、会话、账号、路由、或转录不匹配
5. 传输、代理、超时、或连接失败
6. 目标拒绝、冷却、或权限失败

> **不要**把网络异常并进「服务端拒绝」的计数里。
> **错误族发生变化可以证明进展，但不能证明成功。**

### 池控制（Pool controls）

**只有在它能回答一个具体的诊断问题、或者用户明确接受一个有界回退时**，才使用预验证池。

**要求：**

- 完整的产物**带溯源**，而不是混合片段
- 已知的会话与新鲜度范围
- **只有在复用测试证明必要时**，才一次性或最小使用次数的消费
- 显式的耗尽行为
- **池接受率、本地生成接受率、以及传输异常** —— 三者**分开统计**
- **一次「无池测试」**，用来揭示采集器是否真能铸造新鲜产物

> **如果移除池子之后所有成功请求都停了，那么生成能力没有解决。**

## 判据（Verification gates）

**以下每一条适用的门都要过：**

1. **干净基线与主动资产哈希已记录**
2. **在外层边界被证明之前，没有做阶段插桩**
3. **trace schema 合法，且阶段顺序稳定**
4. **每一个被移植的阶段在确定性向量上通过**
5. **最终解码字节与 wire 产物一致**
6. **负向拼接或篡改对照的行为符合预期**
7. **新鲜的活体业务回放重复成功**
8. **会话、新鲜度、与复用范围已说明**
9. **交付类别被如实报告**
10. **最终采集器在没有活体浏览器或页面上下文的情况下工作**

### 如实报告项（Delivery record）

**必须报告：**

- 主动资产与运行时哈希
- 外层边界，以及**选定的阶段检查点**
- 阶段追踪路径，以及**第一个分叉的结果**
- 分段图与不透明字段
- 确定性对齐向量
- profile 原子性与负向对照结果
- 新鲜度、会话、复用、与路由范围
- **无池测试结果**
- **交付类别：算法化 / 快照驱动 / 池回放**
- **最终的 browser-free 与 runtime-free 状态**

> ⚠ **不构成完成**的典型情形：
> - 「编译通过」
> - 「token 形状对」
> - 「helper 能加载」
> - 「池接受率 95%」—— **那恰恰说明池子掩盖了生成问题**

## 常见坑（Common traps）

- **在外层边界被证明不够之前**，就去插桩每一条 opcode
- **凭一个样本给不透明字节命名**，然后又去随机化它们
- **修复更靠后的分段**，来掩盖**第一个真正分叉的阶段**
- 把**完整成功的 profile** 混入**从未观察过的组合**
- 把**高池接受率**当作「能新鲜生成」的证明
- **把捕获的产物嵌进源码**，却没有溯源或过期控制
- 把**快照驱动的生成**称为「完全算法化」
- 把**编译成功、token 形状、或 helper 能加载**当作活体接受
- **在一条新鲜的无池回放稳定之前**，就扩并发
