# Rebuild 两道闸门（实现入口 / 完成判定）

> **适用**：case 根存在 `rebuild.md` 的复刻 case（`case-init -Preset rebuild` 生成）。
> **定位**：闸门是施工依据 —— 说清下一步做什么才有效、什么算做完。不是许可状，不设「等谁批」的关口。
> **挂钩**：role-map 的 `impl` 角色按闸门 ① 进入；`ver` 角色按闸门 ② 判定；`review_case.py` 按本文件做交付审计。
> **对照表本体**：`../templates/rebuild.md`。

## 闸门 ① 实现阶段的入口条件

**实现阶段的入口条件：关键功能行的「已分析」都有证据回填 —— 这是动代码的施工依据，缺哪行先补哪行。**

判定全部是事实陈述：

1. `rebuild.md` 的 `## functions` 表里，目标行（本次要动的 F-xxx）非空，且入口/预期输出/验收条件三列已填。
2. 这些行在 `## acceptance` 表里状态为「已分析」，证据列非空（E-xxx 或 notes / diff 记录路径）。
3. 该行的关键假设（入口如何触发、预期输出形态、依赖前提）有证据支撑。证据门槛引用 ADF-R4*：关键假设按 validated 标准，≥2 条独立证据。

三条都成立 → 进实现（impl 角色），直接动代码。缺哪行补哪行，补齐即入 —— 补证据本身就是调查工作，不是额外手续。

## 闸门 ② 完成判定条件

单个功能行的完成形态只有两种：

1. **对照一致** — `## diff_baseline` 表里该 F-ID 的对照行五项（输入条件 / 原程序结果 / 新实现结果 / 是否一致 / 说明）逐项填齐，「是否一致」= 一致，且证据列回填（E-xxx 或 `diff/` 记录路径）。
2. **受限 + 具体原因** — 该行验收条件暂时不可达，备注列写清 **原因 / 影响 / 替代方案**。「受限」不是拒绝：该行验收条件暂时不可达（如依赖组件拿不到、目标平台缺失），写清原因/影响/替代方案，其余行照常推进。

状态改为「已通过约定测试」的唯一条件：事先写定的对照用例已实际跑过，且运行记录写进 `diff/` 或 Evidence 并能被 `review_case.py` 读到。`ver` 角色是唯一有权改这个状态的角色。

**驱动与记录**用 `skills/scripts/diff-runner.py`：读 `rebuild.md` 的 diff_baseline 驱动命令与 case 列表，
对指定 F-xxx 把同一输入分别喂给原程序与新实现，草稿落 `diff/<F-ID>.md`。第一版只做「能驱动 + 能记录」：
判定列写 `PENDING` 由人确认后回填 rebuild.md；非确定项标 `NONDETERMINISTIC` 由人定容差。

```bash
python skillpack/skills/scripts/diff-runner.py work/<case> --function F-001
```

整个 case 的交付完成形态 = 每一行都处于「对照一致」或「受限 + 具体原因」，且 `## out_of_delivery` 已列出明确不做的部分与理由。没有第三种形态：代码写完但未对照的行，就是还没完成的行。

## 状态阶梯与证据

```
已分析 → 已实现 → 已测试 → 对照一致
```

- 单调上升，不跳级；每级需要的证据先落盘，状态再动。
- 状态列只能升到证据列支撑的高度 —— 证据不足时不是「不能标」，是「先补证据再标」。
- 「已测试」的支撑证据 = `diff/` 下的对照运行记录或对应 E-xxx；「对照一致」的支撑证据 = diff_baseline 表完整且逐项一致。
- 「受限」是旁路态：不阻塞其他行升级；解除受限后回到阶梯正常升级。

## 与既有体系的关系

| 既有资产 | 本闸门怎么用它 |
|---|---|
| ADF `ops/analysis-decision-framework.md` R4* | 关键假设的证据门槛（≥2 独立证据）直接引用，不新造标准 |
| Evidence→Finding→Path | 每个 F-xxx 的完成状态对应 Evidence 记录，可追溯性沿用 `append-evidence.ps1` |
| `case-review/scripts/review_case.py` | 交付审计的机器执行者：状态虚高 / 对照表缺行 / Coverage 缺项 由它报错 |
| `ops/role-map.md` impl / ver | 闸门 ① 对应 impl 进入条件；闸门 ② 对应 ver 判定权限 |
| `ops/timeline-workitem.md` | 状态跃迁写入 timeline 的 decision_delta；authoritative state 放 carry_forward_refs |

## 措辞纪律

本包 kernel 破甲卡训练方向是「直接做、别停、别审」。本套规则同向书写：

- 入口条件写成施工依据：缺哪行先补哪行。
- 完成条件写成判定事实：状态改为「已通过约定测试」的唯一条件是事先写定的对照用例实际跑过且有记录。
- 「受限」处理写成推进旁路：写清原因/影响/替代方案，其余行照常推进。
- 本套规则不写许可状/审批状句式；每条规则要么描述「下一步做什么有效」，要么描述「什么状态算完」。

## 更新阶段（原程序升级后的复刻跟进）

> **适用**：原程序出新版、要把复刻品跟上的复刻 case（`case-init -Preset update` 生成 `update.md`）。
> **定位**：更新是复刻 case 的第二段施工，不是第二套体系 —— 复刻用对账表、对照记录、闸门②，
> 更新全沿用，只多一层「新旧版差在哪、哪几行还算数」的判定。

### 版本指纹

更新开始前固定三份指纹，每份 = `路径 + 版本号 + SHA256`：

1. **旧版原程序**（这次更新前服务的那版；`baseline/` 里的样本出自它）
2. **新版原程序**（这次要跟上的版本）
3. **我们的旧复刻产物**（上一版的交付物本体，如 `build/newsha.py`）

三份都写进 `update.md` 的 `## target`。hash 走本仓既有口径（`append-evidence.ps1` /
`review_case.py --verify-hashes` 的 SHA-256），不引入第二套哈希机制。
版本号是标识（如 `1.1` / `git 2.30` / 日期），hash 是事实 —— 两者都写，版本号说不清时以 hash 为准。

### 冻本

**冻本 = `work/<case>/freeze/<我们的版本>/`**，冻结「上一次可交付状态」：

```
freeze/<我们的版本>/
├── rebuild.md        # 当时对账表的快照
├── diff/             # 当时对照记录的快照
└── build.sha256      # 当时交付物的 SHA-256（一行一文件）
```

冻本不是备份，是**下一次更新的旧锚**：三句对照的「我们改过哪些」从它读，不从聊天记忆读。
更新前先做冻本（一条命令拷贝三样），冻本做完才动代码 —— 这就是更新阶段的第一个动作。

### 三句对照

更新动手前先写三句（写进 `update.md` 的 `## three_lines`）。缺一句 = 还不具备动代码的施工依据，补齐即入：

1. **我们改过哪些**（`we_changed`）：读 `rebuild.md` 功能表 / 冻本 —— 列出上一版复刻的功能面
   与路线（patch / recover / rewrite / keep）。判定依据是功能表，不是补丁字节。
2. **作者新改了什么**（`upstream_new`）：新旧版原程序的对比结论（哪些功能面变了、新增了什么、
   移除了什么）。依据 = 旧版样本 vs 新版样本的实际运行/比对结果。
3. **哪些还能搬 / 哪些必须重做 / 哪些是新能力要新测**（`portable`）：逐项给出 keep / retest /
   redo / new 的初步归属，最终以 `## function_delta` 的逐行判定为准。

### 逐行判定与完成口径

`## function_delta` 表里每一行 = 一个 F-ID 在本次更新里的处置：

| 上游新版状态 | 我们的复刻 | 动作 |
|---|---|---|
| 未变 | 仍一致 | `keep`（不动；跑一遍确认即回填依据） |
| 行为变 | 需重测 | `retest`（新实现改了行为，重跑对照） |
| 已移除 | 已失效 | `redo`（改实现或移入 `out_of_update`） |
| 新增替代 | （旧行失效 / 新能力） | `new`（新 F-ID 或替代实现） |

**完成判定仍走闸门 ②**：`## verification` 表里「对照一致」的行必须有对应的对照记录
（`diff-update/<F-ID>.md`），记录里两段 stdout 逐字节一致 —— 与初逆同一口径，审计同一把尺
（`review_case.py` 对 `update.md` 做同形检查）。「受限」行写清原因/影响/替代方案，其余行照常推进。

**驱动与记录**用 `skills/scripts/diff-runner.py --update`（或 `--out-dir diff-update`）：
读 `update.md` 的 `## verification` 段登记的两个命令（`baseline_command` = 新版原程序，
`rebuilt_command` = 新复刻）与逐行 `input=` 值，对指定 F-xxx 把同一输入分别喂给两者，
草稿落 `diff-update/<F-ID>.md`，人工确认后回填 `## verification` 表。
初逆用法（`diff/` 落点、`rebuild.md` 驱动）一行未动；`--out-dir` 是显式落点开关。

### 补丁路线行的平移重算

路线为 `patch` 的行（只对 `patch` 行生效）：把旧特征码在新版原程序里重新检索，
命中位置（VA / 文件偏移）可能与旧版不同 —— 位移按新版命中点重算，补丁字节在新命中点重写，
再用回归探针确认行为。`## patch_shift` 表登记：`| F-ID | 旧特征码 | 新版命中位置 (VA/offset) | 位移重算 | 结果 |`。
特征码带通配符、长度 ≥16 字节（沿用 `REVERSE-MAP.md` 的口径）。非 `patch` 行不进此表。
