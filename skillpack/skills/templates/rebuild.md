# Rebuild 对账表（复刻交付契约）

> 一个复刻 case 的核心状态文件，位于 `work/<case>/rebuild.md`。
> `case-init -Preset rebuild` 生成骨架，随推进逐行回填。
> 两道闸门（实现入口条件 / 完成判定条件）与措辞规则见 `../ops/rebuild-gates.md`。
> 与 scope.md 的分工：scope 管「能不能打」，本表管「交付什么、做到哪、凭什么算做到」。

## target

> 最终交付什么。一行说清产物形态与落点，验收时对照这一行判「交付物是否交出来」。

- deliverable: `<最终交付物：可执行文件 / 补丁 / 库 / 脚本 / 数据文件，含落点路径>`
- form: `<exe | dll | apk | script | library | patch | other>`
- notes: `<交付边界、运行环境、依赖前提>`
- upstream_version: `<原程序版本标识：版本号 / 日期 / git hash；更新阶段读它做版本指纹>`
- our_version: `<我们的复刻版本标识；冻本目录 freeze/<我们的版本>/ 用它命名>`

## functions

> 一行一个功能。ID 从 F-001 起编。
> 路线（每行自选，可混合）：
> - `patch` —— 补丁：只改原程序的指定字节/指令
> - `recover` —— 源码恢复：从反编译结果重建可编译源码
> - `rewrite` —— 仿写：按行为契约重写，不携带原程序代码
> - `keep` —— 保留原组件：该功能直接复用原程序模块，只做接口适配
> - `blocked` —— 受限：该行验收条件暂时不可达（见 acceptance 表备注）
>
> 入口 = 触发该功能的界面 / 命令行 / API / 文件格式入口。
> 预期输出 = 该功能产生的可观察结果（输出文件、stdout、状态码、内存/协议效果）。
> 验收条件 = 可判定的通过标准，写「能说出命令与产物」的形态。

## acceptance

> 四态阶梯（单调上升，不跳级）：`已分析` → `已实现` → `已测试` → `对照一致`。
> - 已分析：该功能的行为已查清并有证据回填（这是实现的施工依据）
> - 已实现：代码/补丁/配置落地，能进入运行路径
> - 已测试：已通过约定测试（事先写定的对照用例跑过，记录在 diff_baseline 表）
> - 对照一致：约定测试的每一项与原程序同输入同输出、行为一致
>
> 特殊态 `受限`：该行验收条件暂时不可达（依赖拿不到、平台不支持等）。
> 受限不是拒绝：写清原因/影响/替代方案，其余行照常推进。
>
> 状态与证据的关系：状态列只能升到证据列支撑的高度。证据 = E-xxx（Evidence 记录）
> 或 diff 目录下的对照记录路径。改状态前先补证据，缺哪行补哪行。

## diff_baseline

> 原程序行为基线位置 + 差异对照表（同输入驱动原程序与新实现，逐行比结果）。
> 表里每个 F-ID 的对照行 = 该功能「已测试 / 对照一致」的证据本体。
>
> 驱动命令字段供 `skills/scripts/diff-runner.py` 读取（`{input}` 替换为每条 case 的值）：
> 两个命令在同一 shell 语义下跑，模式/编码这类环境差异要在命令里固定住
> （例：`sha256sum -t` 固定文本模式）。

- baseline_dir: `baseline/`（原程序样本、快照、原始输出）
- diff_dir: `diff/`（对照运行产物；由 diff-runner 或手工执行生成）
- baseline_command: `<驱动原程序的命令；{input} 占位>`
- rebuilt_command: `<驱动新实现的命令；{input} 占位>`
  两个命令都可用 `{tool:<id>}` 让探测层解析工具路径（例：`{tool:python}`、`{tool:r2}`），
  换机后不用改；也可继续直接写命令行。解析不出来时该 case 判红，不会把占位符丢给 shell。
- harness: `<可选：更复杂驱动脚本的说明>`

  - F-001 | input=`<第一组输入>`
  - F-001 | input=`<第二组输入>`
