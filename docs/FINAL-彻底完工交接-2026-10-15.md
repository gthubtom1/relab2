## 4. 部署层缺口：我们缺的不是零件，是「门面」

### 4.1 我们已有的（其实比 REA 重）

| 零件 | 位置 | 作用 |
|---|---|---|
| 仓根定位 | `relab2-root.ps1` | 写 `REVERSE_SKILL_ROOT`（User 级），多位置探测 |
| 环境初始化 | `setup.ps1`（`-DryRun` / `-WriteMachine`） | 写环境变量 + 调 `selfcheck.ps1` |
| 部署自检 | `selfcheck.ps1` | 退出码即结论 |
| 技能注册 | `skills/scripts/register-skills.ps1`（`-WhatIf` / `-Revert` / `-Doctor` / `-Json`） | **一份实体 + N 个目录联接**，挂进各智能体约定目录 |
| MCP 切换 | `skills/scripts/switch-mcp.py`（`daily` / `full` / `show`） | 在活跃注册表与全量池之间切 |
| 卡片融合工作台 | `kernel/04-console`（`start-console.bat`） | 选智能体 → 勾三段卡 → 载入/卸回，带备份与逐字节还原 |
| AI 安装说明书 | `skillpack/AI-INSTALL.md` | 给 AI 读的安装流程 |
| 换机手册 | `环境初始化.md` §11（含 §11.5 十二步顺序、§11.6 三个已知坑） | 人读着做 |

### 4.2 缺口

**没有统一入口，也没有 `doctor`。** 现在要跑起来，人得知道：
`relab2-root.ps1` → `setup.ps1` → `register-skills.ps1` → `switch-mcp.py` → `start-console.bat` → 勾三段 → 载入 → `selfcheck.ps1`，
而且顺序、参数、注意点散在 5 份文档里。**这就是「部署非常麻烦、没有稳定性、不像开源项目」的真相。**

### 4.3 要建的东西（对应 REA 的门面）

| 命令 | 行为（对齐 REA） |
|---|---|
| `doctor` | 一条命令报「本机现在能不能干活」：仓根 / 环境变量 / 工具探测 / 4 条 MCP 通道（注册·监听·怎么起）/ 技能挂载 / 卡片融合 / 门禁。**全绿才叫就绪** |
| `setup` | 幂等；`-DryRun` 只给计划（确切路径、备份、改动）；自动备份；把上面那串全串起来 |
| `update` | 换机 / 升级同一条：拉取 → 重跑 setup → doctor |

**判据**：一台干净 Windows 上，`clone` → 跑一条 `setup` → 跑一条 `doctor` 全绿 = 就绪。**不允许中间再出现「你来问、我来答」。**

## 8. 部署门面 + 工具通道自动拉起（2026-10-15 01:30，②③ 完成）

> 本节记的是**机制**，不写任何本机探测出来的路径（遵守 `环境初始化.md` §10）。
> 机器相关的绝对路径只活在宿主的 `mcp.json`（机器状态，不是文档）。

### 8.1 建了什么

| 文件 | 作用 |
|---|---|
| `<仓根>/relab2.ps1` | **门面**：`doctor`（一条命令报本机能不能干活）/ `setup`（幂等，`-DryRun` 只打印计划）/ `update`（换机、升级同一条） |
| `<仓根>/skillpack/skills/scripts/mcp-lazy-http.py` | **懒启动代理**：把 HTTP 型 MCP 通道包成 stdio，工具常驻可见、后端按需拉起 |
| `<仓根>/skillpack/skills/scripts/switch-mcp.py` | `daily` / `full` 合并（懒启动上线后不再需要切来切去；原 `daily` 会把 3 条通道从活跃配置里删掉，是个静默回退陷阱） |

### 8.2 懒启动代理的三条铁律

1. **启动代理进程绝不启动后端** —— 否则每开一次宿主就弹一次 x64dbg / 起一次 IDA。
2. `tools/list`：后端在 → 取实时清单并刷新缓存；后端不在 → **直接回缓存清单**，所以工具对模型永远可见。
3. `tools/call`：后端不在 → 跑启动器、自己轮询端口、再转发；超时或失败 → 回一条**写明试过什么、下一步敲什么**的错误，绝不挂死。

| 场景 | 结果 |
|---|---|
| 后端在监听 | `tools/list` 取到实时 **69**（IDA）/ **80**（x64dbg）个工具，并写缓存 |
| 后端**被关掉** | `tools/list` 仍返回 **69** 个，日志记 `from cache`，**没有触发任何启动** |
| 后端关闭时**调用工具** | 日志 `port closed -> launch` → **9 秒后端口监听** → `call idb_list ok`，返回真实结构化结果 `{"sessions":[],"count":0}`；总耗时 18.5s |
| 启动器超时/失败 | 返回明确错误文本 + 日志路径，**8 秒返回、不挂死** |
| 宿主注册 | `mcp.json` / `mcp.all.json` 里 4 条通道**全部改成 stdio**（原 idapro / x64dbg-mcp 是 http），已带 `.bak-lazy-*` 备份 |

> ⚠️ **生效条件**：宿主的 MCP 注册表在**会话启动时**读取。这条改动要**重启宿主 / 新开会话**才生效。

### 8.4 已知取舍（不是缺陷，是账）

- 工具常驻可见意味着**工具 schema 占用上下文**（IDA 69 + x64dbg 80）。换来的是"不用再提醒它去起通道"。
- x64dbg 的 Bearer token 是**每个实例自己的**，写死在宿主 `mcp.json` 里（与改动前一致）；x64dbg 换实例后要同步那个 token。

④ `lcs-core/05`、`06` 回炉 · ⑤ 补 `01a135bf` 需求档案 · **⑥ 真实验收（未见过的目标、零提示）** · ⑦ 推 GitHub + 清旧中枢仓库。
⑥ 仍是唯一不能靠门全绿替代的一关。

## 10. 能力发现层 + 工具补装（2026-10-15 02:00）

### 10.1 为什么要有「能力发现」，而不是「工具清单」

原设计按**工具名**找（`Resolve-ReverseToolSpec -Name <id>` + 36 条别名表）。
换一台机器、装的是别的同类软件、名字我们没见过 —— 那张表就废了，只能人肉打补丁。
主人的要求是：**任何机器、任何同类软件，只要装在机器上就能被认出来、被调用**。

**新增 `skills/scripts/capability-index.py`（能力索引）**：
1. 扫 PATH + 工具根（限深度、排除依赖目录、**复用 `_map.json` 的 deny / notHere 判断**）；
2. 先按**规则**归类（规则表，不是清单）；规则认不出的，跑一次 `--help`（限时 2s）抓关键词兜底
   —— **没见过的新工具也能归位**；
3. 去重排序（工具根 `cli/` 下的 wrapper 优先），每能力最多留 12 个；
4. 落地到机器状态目录，**不入库**；查询用 `--find <能力>`。

**实测**：扫 4828 个候选、12.9 秒，识别 25 类能力。刚装的 ffuf / nuclei / scrcpy / node / yr
**没有人给它们登记过任何东西**，全部被自动认出来并归到「目录爆破 / Web 扫描 / 设备桥接 / JS 运行时 / YARA」。

### 10.2 接进 MCP

`relab2-tools-mcp.py` 新增 `find_capability(capability)`：
问「谁能解固件 / 谁能反编译 / 谁能抓包」→ 返回本机能干这件事的工具。实测 1.2 秒返回。
> 实现坑：一开始用子进程调 `capability-index.py`，在 stdio MCP 服务器里会把调用拖住（>250s）；
> 改成**同目录 import、进程内调用**后恢复正常（1.2s）。
