## 1. 唯一必做缺口：操作者姿态（为什么这是缺口，白话版）

### 1.1 先说个比方，你就懂了

主人的原话（大意）：

> 「我们这个项目，就像一个小孩子，手里拿着一大堆武器，但是没有办法好好利用。」

再具体点。我们的项目里有：
- 47 个技能（怎么逆向 APK、怎么逆向 .NET、怎么处理 Go/Rust、怎么搞固件……）
- 472 篇文档（VMP 去虚拟化、license keygen 七篇、OLLVM 反混淆、反调试 A-T 菜谱……）
- 133 个脚本、25 条门禁、探测层、MCP 通道

**VMP 那两篇文档质量高到世界级**——VM entry 定位四步法、dispatcher 三段式、
三级降级策略、等价性验证脚本，全都有。

**但是**：主人真的拿一个 VMP 样本丢给 AI，AI 会走哪条路？

会走 `reverse-engineering/SKILL.md` 里的「Problem-Solving Workflow」八步：
```
1. strings 提取 flag → 2. ltrace → 3. Frida hook strcmp → 4. angr → 5. Qiling
```

**这五件在 VMP 面前全军覆没**：没有明文、没有 strcmp、angr 一进解释器循环就路径爆炸。
而那份世界级文档挂在 `Additional Resources` 第 83 行，AI 要自己想到才会打开。

**这就是「有武器不会用」。** 前一轮已经修好了这个入口问题（assault-entry.md 分流器）。

### 1.2 但还有更深的一层：没有「人」

前一轮修好了「该拿哪把武器」。但还有一层没人管：

**没人告诉 AI「面对未知目标时，该用什么姿态思考」。**

我们的 472 篇文档，每一处都假设 AI 是**不会主动判断的执行体**——所以什么都写成判据表：
字段表、状态表、分层表、过层判据、出口条件……极其完备。

结果是：**纪律很好，但不会判断。**

一旦目标超出判据表的覆盖范围（**真实硬目标必然超出，这就是"硬"的定义**），
AI 就没有然后了——它只能照着表走，表上没写的它不会。

### 1.3 对比一下就明白差距在哪

主人在讨论中提到另一个项目 `github.com/morluto/rea`（REA），说朋友用它三小时
破解了一个 VMP 软件。实测之后发现：

**REA 只有 237 行 SKILL.md**，极少写"你要严谨、要查漏、要有耐心"。
它做什么？把**工具层做厚**——每个目标类型都有专门工具、专门 guide、专门 schema。
然后**把判断留给模型本身**。

**我们正好相反**：工具层散在 472 篇文档里，判断层是空的。

（补充说明：REA 那个"三小时破 VMP"有 hype 成分，第三方横评发现同题对比下
不用 REA 的裸 agent 反而先完成。但这里不讨论它是不是被神化了——
**它那个"工具厚、判断交给模型"的结构是对的，值得我们学的就是这个结构，不是它的代码。**）

### 1.4 所以本项目是三维的，不是两维

| 维度 | 是什么 | 状态 |

| ① 系统 | 入口 / 对账表 / 分层判据 / 状态机 / 审计器 | ✅ 前一轮已建 |

### 1.5 攻坚者五条（本次要补的东西，原文照此落地）

**这五条不是判据表，是姿态。** 判据表决定系统完不完备，这五条决定人行不行。

**① 分清搬运工和货物**
在壳层（L1）里花的每一分钟，都要问一句「我改的是搬运工还是货物」。
壳是搬运工，业务逻辑才是货物。判定点几乎从不在 L1。
**停在壳层打转 = 项目没推进，无论做了多少工作。**

**② 工具输出是线索，不是结论**
`diec` 报的壳类型、反编译出的伪码、`strings` 抓到的常量、`capa` 命中的能力——
**全部是线索，没有一个是事实**。反编译器会把 `__ftol()` 当返回值而藏起真实输入
（这是 REA 的 DX-Ball 案例实证）；VMP 静态看到的立即数是 VM key 加密过的假值。
**结论必须由两条以上独立证据交叉支撑**（项目里已有这规矩：ADF-R4*，validated 需 ≥2 独立证据）。

**③ 优先查矛盾，不优先查顺利**
顺利的地方最不用看。真正值钱的是「不对劲」：反编译结果和行为对不上、
导入表干净得可疑、两份证据互相冲突、函数名叫 A 但干的事像 B、静态与动态结论相反。
**矛盾就是入口。** 遇到矛盾不许选一个顺眼的放下，要查清为什么不一致。

**④ 宁可写卡住，不许写完成**
「我卡在 U-007，原因是 VM context 进出被 XOR 变换，静态拿不到布局」是**有效交付**。
「已完成」但没有对照证据是**无效交付**。
门禁绿、程序能启动、代码写完了、报告很厚——**这四件事单独一件都不等于成品**。

**⑤ 调整路线是正常的，不调整才不正常**
真打硬目标，第一次选的路线大概率不完整。一边打一边修正是人的工作方式，
也是 AI 该有的方式。调整不是失败，是进展——但每次必须写清
「旧路线为什么不通 / 新证据是什么 / 新路线凭什么更可能通」，
记进 timeline 的 `decision_delta`。**一次都没调整过的攻坚记录，默认是编的。**

**五条的根源**：终点只有一个——可运行、可验证、功能等价的成品。
每一步动手前问「这一步是否让成品更近」，答不上来就是白做。
**难度花在 `how` 上，永远不花在 `whether` 上。**

## 4. 判据口径（防止自欺）

- 未实跑不许写「已实测」。本机跑不了的写「本机未实测」

  **不许用「日志里出现我自己写的标记」当判据**——项目里有一张经验卡专门记这条

- 「门禁绿」只代表该门禁这一次的结果，不代表功能达成。
- 同一方法连败两次 → 换方法，不许在原路线上加第三个补丁。
