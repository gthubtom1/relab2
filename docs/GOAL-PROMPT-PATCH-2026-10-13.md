### 1.1 为什么这是缺口（前几轮反复返工的真原因）

项目有 47 个技能 + 472 篇文档，**每一处都假设 AI 是不会主动判断的执行体**——

但它把**工具层做厚**、把**判断留给模型**。我们正好相反——工具散在各处，判断层是空的。
一旦目标超出判据表覆盖（**硬目标必然超出**），AI 就没有然后了。

**本方案从此是三维的，不是两维**：

| 维度 | 是什么 | 现状 |

| ① 系统 | 入口 / 对账表 / 分层判据 / 状态机 / 审计器 | ✅ 前一轮已建 |

| ③ **操作者** | **面对未知时怎么想、怎么判断、怎么不自己骗自己** | ❌ **本次唯一要补** |

**缺①是散沙，缺②是空谈，缺③是「纪律很好但不会判断的部队」。**

### 1.2 攻坚者五条（原文照此落地，不许改语义）

**① 分清搬运工和货物**
在壳层（L1）里花的每一分钟，都要问一句「我改的是搬运工还是货物」。
壳是搬运工，业务逻辑才是货物。判定点几乎从不在 L1。
**停在壳层打转 = 项目没推进，无论做了多少工作。**

**② 工具输出是线索，不是结论**
`diec` 报的壳类型、反编译出的伪码、`strings` 抓到的常量、`capa` 命中的能力——
**全部是线索，没有一个是事实**。反编译器会把 `__ftol()` 当返回值而藏起真实输入
（DX-Ball 实证）；VMP 静态看到的立即数是 VM key 加密过的假值。
**结论必须由两条以上独立证据交叉支撑**（ADF-R4*：validated 需 ≥2 独立证据）。

**③ 优先查矛盾，不优先查顺利**
顺利的地方最不用看。真正值钱的是「不对劲」：反编译结果和行为对不上、
导入表干净得可疑、两份证据互相冲突、函数名叫 A 但干的事像 B、静态与动态结论相反。
**矛盾就是入口。** 遇到矛盾不许选一个顺眼的放下，要查清为什么不一致。

**④ 宁可写卡住，不许写完成**
「我卡在 U-007，原因是 VM context 进出被 XOR 变换，静态拿不到布局」是**有效交付**。
「已完成」但没有对照证据是**无效交付**。
门禁绿、程序能启动、代码写完了、报告很厚——**这四件事单独一件都不等于成品**。

**⑤ 调整路线是正常的，不调整才不正常**
真打硬目标，第一次选的路线大概率不完整。一边打一边修正是人的工作方式。
调整不是失败，是进展——但每次必须写清「旧路线为什么不通 / 新证据是什么 /
新路线凭什么更可能通」，记进 timeline 的 `decision_delta`。
**一次都没调整过的攻坚记录，默认是编的。**

**五条的根源**：终点只有一个——可运行、可验证、功能等价的成品。
每一步动手前问「这一步是否让成品更近」，答不上来就是白做。
**难度花在 `how` 上，永远不花在 `whether` 上。**
