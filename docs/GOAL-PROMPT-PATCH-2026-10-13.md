## 0. 你是谁、你在哪、要干什么

### 0.1 这个项目是什么

主人在做一个 AI 逆向工程技能体系（`C:\relab2`），**主人是零基础，
不会写提示词、不会跟 AI 精确沟通**。他要的是：给一个软件，AI 自己搞完，

项目目标（主人原话的意思）：

> **给 AI 一个软件（exe / APK / 固件 / 网站客户端，什么都行），

> 最后交出一个「所有功能都正常、我能直接用」的成品。**

拆成四条，一条都不能少：

**① 终点是成品，且成品要功能完整。**
主人原话：「**能够使用成品的所有的功能。所有的功能都要正常。**

**我只要最终的成品，就是我能够正常使用的，它的所有功能都是正常的。**」

→ **「能启动」「界面像」「主要功能可用」都不算成品。**

**③ 路线不预设，允许中途改。**
可能该打补丁、可能该恢复源码、可能该照行为重写、也可能某个模块留原样只做适配。
不同模块走不同路线是正常的。**一开始选的路线大概率不完整，
一边打一边修正是人的工作方式，也该是 AI 的方式。**
一次都没调整过路线的攻坚记录，默认是编的。

**④ 不是所有任务都是逆向（这点对主人很重要，他日常要用这套东西）。**
主人原话：「日常开发和攻坚**一半一半**」。

**该触发什么技能就触发什么技能，该用什么工具就用什么工具，

## 1. 唯一必做缺口：操作者姿态（若 §0.0 自查发现没做，才做；做了就抽查）

### 1.1 为什么这是缺口（白话版）

项目有 47 个技能、472 篇文档，**每处都假设 AI 是不会主动判断的执行体**——
所以什么都写成判据表、字段表、状态表。结果是纪律极完备，但不会判断。
真实硬目标必然超出判据表覆盖（**这就是「硬」的定义**），超出去 AI 就没有然后了。

对照 REA：它只有 237 行 SKILL，极少写「你要严谨」，因为它把**工具层做厚**、
把**判断留给模型**。我们正好相反——工具散在各处，判断层是空的。

### 1.2 本项目从此是三维的

| 维度 | 是什么 | 现状 |
|---|---|---|
| ① 系统 | 入口 / 对账表 / 分层判据 / 状态机 / 审计器 | 已建 |
| ② 工具 | 47 技能 / 472 文档 / 133 脚本 / 探测层 | 早有 |
| ③ **操作者** | **面对未知怎么想、怎么判断、怎么不自己骗自己** | 刚补 / 你复查 |

**缺①是散沙，缺②是空谈，缺③是「纪律很好但不会判断的部队」。**

### 1.3 攻坚者五条（原文照此落地，不许改语义）

**① 分清搬运工和货物**
在壳层（L1）里花的每一分钟，都要问「我改的是搬运工还是货物」。
壳是搬运工，业务逻辑才是货物。判定点几乎从不在 L1。
**停在壳层打转 = 项目没推进，无论做了多少工作。**

**② 工具输出是线索，不是结论**
`diec` 报的壳类型、反编译伪码、`strings` 常量、`capa` 命中——**全是线索，没一个是事实**。
反编译器会把 `__ftol()` 当返回值而藏起真实输入；VMP 静态立即数是 VM key 加密的假值。
**结论必须由两条以上独立证据交叉支撑**（ADF-R4*）。

**③ 优先查矛盾，不优先查顺利**
顺利的地方最不用看。值钱的是「不对劲」：反编译与行为对不上、导入表干净得可疑、
两份证据冲突、函数名叫 A 干的像 B、静态与动态结论相反。
**矛盾就是入口。** 遇到矛盾不许选一个顺眼的放下，要查清为什么不一致。

**④ 宁可写卡住，不许写完成**
「我卡在 U-007，因为 VM context 进出被 XOR 变换」是**有效交付**。
「已完成」但没对照证据是**无效交付**。
门禁绿、程序能启动、代码写完、报告很厚——**这四件单独一件都不等于成品**。

**⑤ 调整路线是正常的，不调整才不正常**
第一次选的路线大概率不完整。一边打一边修正是人的工作方式。
调整不是失败，是进展——但每次必须写清「旧路线为什么不通 / 新证据是什么 /
新路线凭什么更可能通」，记进 `decision_delta`。
**一次都没调整过的攻坚记录，默认是编的。**

**五条的根源**：终点只有一个——所有功能正常、可直接使用的成品。
每步动手前问「这一步是否让成品更近」，答不上来就是白做。
**难度花在 `how` 上，永远不花在 `whether` 上。**

## 3. 派无上下文子代理做最终验收（硬性，不许省）

**不许省，也不许主人手动触发。** 你走到这就自己派。

### 3.1 为什么

你和这套东西共享太多上下文，分不清「它没问题」和「我没看出问题」。
需要一个**没有上下文**的审查者自己判断。**它跟你的模型不一样，视角不同。**

### 3.2 怎么做

1. 读 `docs/FINAL-ACCEPTANCE-BRIEF.md`。**那是需求陈述，不是检查清单。**
2. 派一个子代理，把那份文件**全文**给它，**不要**加工、**不要**拆清单、
   **不要**提示「重点查哪」。它有工具权限，能自己 open 文件、跑命令。
3. 等它交报告，然后你**自己**做三件事：
   - 它报告的每一条问题**打开文件验一遍**（它可能误报，也可能说轻了）
   - 该修的修（红线照旧）
   - 报告原文 + 你的复核结论，一起追加进 `docs/ASSAULT-GOAL-2026-10-13.md` 的
     `## 9b 无上下文最终验收 · <时间>`

### 3.3 三条铁律

**① 不许替它回答。** 它交报告前，你不许暗示「我觉得问题在 X」。
它查不出来只有两种可能：真没问题，或没真查。你自己判断是哪种，
把判断写进 9b——**但要有依据，不许写「经复核确认无误」。**

**② 它说没找到问题时，你要么找出它漏了什么，要么承认它查得对。**
最差的处理是直接抄它的结论交差。

**③ 报告要让人看得懂「它怎么得出结论的」**，不只是结论。

## 4. 实弹攻坚：拿真实目标打出成品（**这是最终验收：成品必须出来**）

**这一步是整套项目的最终验收。前面全是准备，这一步才是开枪。**

**主人原话（照着做，一个字都别改）**：

> 「以**必须打穿**为目标。你不能在文本里写『可以打不穿』——
> 因为你一写，它就偷懒：遇到困难就说反正打不穿也行，就跟主人说打不穿就可以了。

**所以本项目只有一条验收线：成品出来了没有。**
