## 4. REA 判定：方向对、位置错；改为「四条工程写法」注入阶段 3

### 4.1 先纠正两个前提

1. **本机装不了 REA 的包**：无 Node.js / npm（`node -v` / `npm -v` 均不存在，`D:\Tools` 与 `C:\Program Files\nodejs` 下无 `node.exe`），REA 要求 Node 22.19+；本机 Ghidra 12.0.2，REA 的 Windows 原生通道要求 12.1.x（JDK 21 满足）。
   → **所以「装」这条路物理上不存在**，这一点无需再讨论。
2. **但「抄它的思路」是对的**，而且是本项目的正解。问题在于 `05`/`06` 抄錯了科目。

### 4.2 逐条对照：REA 有的，本项目有没有

| 维度 | REA 的做法 | 本项目现状 | 判定 |
|---|---|---|---|

### 4.3 结论：要注入的是这四条（全部属阶段 3 范围）

1. **工具手边化**：入口卡写死优先级「**MCP 通道 > CLI 孪生 > GUI**」，并给出 4 个通道各自的**一行启动命令**；只在实际要用该通道时启动（这一条与 REA 的 "connect only when needed" 一致）。
2. **第一屏即路由**：把「目标形态 → 第一个工具」一屏表提到总入口第一节；把「必须立即执行的 4 步契约」下沉（它现在是第一屏，等于让模型先办四道手续才准碰目标）。
3. **删掉「动手前先自检」**：改成「**只有观测到阻塞**（通道 closed / 工具报错 / 拿不到结果）才去唤醒或诊断」。
4. **大结果不进上下文**：任何 >N KB 的工具输出先落盘，再分页读（本项目目前没有这条纪律）。
