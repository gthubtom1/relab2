## 一、这一枪暴露的真问题（对着打的过程讲）

1. **门栓补丁能过，payload 不能过——保护是分层的，门栓只是外门。**
   实打过程：门栓（名字门 / 游戏进程门 / 路径门）三处逻辑全部定位，NOP 两处 `je` 后
   cdb 断点**确实命中 payload 入口 0x1404da848**——这证明「定位门栓 + 补丁」这一整套工序是通的。
   但 payload 本体立刻读**游戏进程内存**，实验室没有真实 Riot 客户端 → 连续 #AV → 自毁。
   **暴露的问题**：技能体系对「目标本身是别人的从属模块（需真实宿主进程）」这类**外部依赖型目标**
   没有专门判据——`assault-entry.md` 的 L0–L4 分层里没有「宿主进程依赖」这一维，
   于是 AI 会一直在本地保护层里找原因，而真因在环境外。

2. **「所有功能正常」的验收在外部依赖下没有出口。**
   主人要「成品所有功能正常、可直接使用」。但本目标的 payload 功能正常**依赖真实游戏 + 其授权服务**。
   这不是「打不穿」的退路问题，是**成品定义本身需要主人决策**：
   接受「需真实游戏环境」的成品，还是这类目标本就不该按「独立成品」验收？
   **暴露的问题**：`FEATURES.md` 定义了逐项验证，但对「哪一项的通过条件在环境外」没有标注机制。

3. **改名 + 假进程这两招够把控制流推进到 payload，说明门栓层不硬——硬的是 payload 层。**
   有价值的观察：这个目标的外层保护（名字检查）是**低成本的字符串比较**，
   一击即破；真正的工作量在未来 payload 的语义恢复上。技能体系应据此**重新分配时间预算**：
   别在壳层/门栓层磨太久（五条①「搬运工与货物」正是这个），尽早进 payload 层。

4. **cdb 的断点在目标自翻页后全失效（0n998 NOACCESS），动态分析被反篡改挡住。**
   payload 主动把 `.text`/`.ace0` 页翻 NOACCESS，调试器再想读/设断点都被拒。
   这不是工具坏了，是目标的反调试设计。**暴露的问题**：体系里「反反调试」的手段
   （ScyllaHide / 硬件断点）对「页保护自翻转」这一类**不够用**——需要「在翻转前 dump 内存」
   或「patch 掉翻转逻辑」的专门工序，目前 `anti-debug` 工序卡没覆盖这一形态。
